---
name: pre-spec
description: Check this Plan Mode's ratified decisions against each other and the vault before the Spec is approved.
---

Run `uv run guppi prespec --check <the plan file of this Plan Mode> --session <id>`, the eight-character session id — the second token of the `hi:` line the `UserPromptSubmit` hook put in the context at `/hi`, between the time and the folder (cases 213.3, 256). Read the first line of the output before the exit code: 'no hi recorded for session …; nothing checked' means the wrong value, and the check did not run. Each line it prints is a finding, except a line that opens with `note:`, which is no finding: it sets no exit code and is answered in one line in the chat (case 378.8). What the check compares is written in the module docstring of `guppi/prespec.py`, beside its code (case 561.1). Fix a finding in the Frontier or in a ledger line yourself, and run the check again until it prints no finding of that kind. A finding in a Case — its prose or its body, a wrong fact of its `context` included — goes to the `case-guppi` of that Case in the loop below; do not edit the text of a Case in the plan (cases 438, 441).

At the first run of `/pre-spec` in the session only, dispatch one `ask-guppi` agent over the plan, or, when the plan's title line names a conserved Spec, over that Spec, with the absolute path of the plan file, the instruction to judge every Case outside the `## Deferred` heading with its sub-cases (case 674.1), and the instruction to read for every Case there outside the `## Deferred` heading its `context`, its `when` and `then` sections and its `then` block — `replace` old and new, `set`, `sections` — and, for an `update` of a rule or an entity, the page's `estimates`, before judging a page, so that a finding can name a wrong wording or a wrong place, and of a Case under `## Deferred` only the slugs of its `defer` items; the agent writes no list of the decisions — the plan is the list (case 388). Three questions: which of these contradict a page of the vault, a rule of the vault, or each other; whether an Estimate the Case does not name speaks of the thing the Case changes — one that does is a finding (case 203.2); which fact of a `context` — a page's status, a count, a case number, a claim that no page holds a thing — the vault does not bear out (case 388). A later run in the session dispatches no `ask-guppi`: each Case built again is checked against the vault and its frame by its own `case-guppi` (case 561.1), and the findings that sent it back are confirmed once in the loop below (case 634.2). The body of a Case under `## Deferred` is not read: the session that takes the defer up judges it with its own pre-spec. A Case of this plan that changes a page another Case of this plan defers is no question for `ask-guppi`: the check prints such a pair as a `note:` line at every run, a change and a defer inside one top-level Case aside (cases 186.2, 726.1).

Answer the findings with one report before any Case is sent back: the list of what the `ask-guppi` run did not check, with no claim that the whole Spec is checked, since one run over a large Spec returns only part of the findings (cases 634.1, 674.1); each finding numbered, with the fix you propose or, in one line, why it is already known; the findings that need no word of the person apart from those that need one; and each decision you need from the person as a question in the shape of `.claude/skills/grill-me/SKILL.md` (case 561.13). Then run the loop (case 561.2):

1. When the report asks the person no question, go on to step 2 at once. Otherwise send nothing to any `case-guppi` until the person has answered every question of the report, since an answer may change a fix. A question the person leaves unanswered you ask again, in its grill-me shape and under its number, and everything stays held (case 595.1).
2. Send each finding in a Case, with each answer of the person that bears on that Case, to the `case-guppi` of that Case by `SendMessage`, all of them in one message.
3. Wait for every `case-guppi` you sent to answer, and pass on no answer of one `case-guppi` alone. An answer to `SendMessage` comes back as a notice that opens a turn of its own, and each turn ends with a reply: end each turn that sends to a `case-guppi`, and each turn that an answer opens while another answer is still out, with one line that opens with a bold label ending in a colon — `**Waiting:**`, translated — and names the Cases that have answered and the Cases still out. Write nothing else in the chat while an answer is out: nothing of what an answer says, and no question; a round that came back waits for the list of step 4, and the label lets the reply pass the check of `rule-case-check` (case 581.1).
4. Show the person one list of what to answer: every round that came back, each question in its grill-me shape, translated as a round of `case-guppi` is, and numbered `<Case id>.Q<n>` — the id of its Case and its number in the round — so that each answer goes back to its `case-guppi`; the `**Context:**` label of each first round names its Case and its Frontier item, translated, such as `**Context — Case 7 (C2):**`, and no heading or other line of your own marks where a round begins (case 699.7).
5. Send each answer to the `case-guppi` of its Case, all in one message, and go on from step 3 until every `case-guppi` you sent has answered with its Case.
6. Send each `ask-guppi` run whose findings sent a Case back the Cases built again on them, by `SendMessage`, all in one message, and ask only whether each of its findings is closed: the message invites no new finding and no new judgment of a Case beyond those findings (case 638); wait for every answer as step 3 sets it. Then ask the person a question after the confirmation, in its grill-me shape: whether each finding not closed is fixed or left; a finding to be fixed goes to the `case-guppi` of its Case as in steps 2 to 5. No Case goes to `ask-guppi` a second time, and no new `ask-guppi` is dispatched (case 634.2).
7. Show every Case built again in one reply, what step 6 found closed and not closed standing in your own text after the horizontal rule, each in the showing that `vault/wiki/orchestration.md` sets, for one ratification.

Inside this loop the rule of `vault/wiki/orchestration.md` that no Case is taken up before the current one is ratified does not hold: the Cases built again go out together and come back together. After their ratification do not call `/pre-spec` again: run the check above and fix what it prints; when it prints no finding, exit Plan Mode. The hook of `rule-prespec-onward` sends you on after the reply that acknowledges the ratification, and the hook of `rule-prespec-hook` refuses the exit while the check prints a finding (cases 561.3, 561.5). A reply with a `LEDGER` block inside the loop before any Case is built again — a defer or a lesson in answer to the report — is sent on by the same hook too: on with the loop, or, when no Case goes back, to the check and the exit (case 686.1).
