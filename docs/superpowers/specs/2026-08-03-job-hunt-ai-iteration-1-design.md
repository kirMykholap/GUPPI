## 1. Задача и границы

### Проблема

Сильный кандидат не получает приглашений на интервью, несмотря на высокую совместимость с
вакансиями. Причины непрозрачны: автофильтры ATS, нерелевантные ключевые слова, формат
документа, время подачи. Инструмент должен убрать эти слепые пятна — собирать вакансии,
измерять совместимость с профилем кандидата, показывать разрывы и накапливать данные для
проверки гипотез.

### Что строим в итерации 1

Сквозной тонкий срез через все слои системы — от резюме до скора:

1. `docker compose up` поднимает приложение и базу
2. Онбординг: загрузка CV (PDF/DOCX) → извлечение тезисов моделью → экран правки тезисов
3. Профиль: целевые роли, города, форматы занятости, стоп-слова
4. Парсеры work.ua и dou.ua: сбор по профилю, дедупликация, отметка закрытых вакансий
5. Матчинг: извлечение требований моделью → BM25 + семантика → гибридный скор
6. Таблица вакансий: скор, gap-анализ, ручная смена статуса отклика
7. Langfuse подключён, есть два размеченных датасета и первый прогон evaluation

На выходе — работающий инструмент плюс слой измерения качества промптов.

### Что осознанно вне итерации 1

| Отложено | Причина |
|---|---|
| Чат AI-интервьюера | Заменён экраном правки тезисов. Качество интервьюера зависит от того, какие тезисы реально нужны матчингу — это выяснится после прогона по сотне живых вакансий |
| Генерация резюме и cover letter в PDF | Требует устоявшегося формата тезисов и откалиброванного gap-анализа |
| Аналитический дашборд, проверка гипотез | Нет данных: пока откликов меньше 20–30, любые выводы о паттернах будут самообманом |
| Аутентификация, мультитенантность | См. решение о local-first ниже |

### Критерии готовности итерации 1

- Оба парсера собирают вакансии по параметрам профиля и не создают дублей при повторных прогонах
- Вакансия, исчезнувшая из выдачи три прогона подряд, помечается неактивной
- CV в PDF и DOCX превращается в редактируемый банк тезисов
- Для каждой вакансии рассчитан гибридный скор и разбор покрытия требований
- Статус отклика меняется из таблицы и сохраняется
- Прогон `evals` по датасету `requirements` выдаёт метрики качества извлечения
- Юнит- и интеграционные тесты проходят; парсеры покрыты тестами на HTML-фикстурах

## 2. Принятые решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Приоритет | Рабочий инструмент для себя | Портфолио — следствие качественно сделанного инструмента, не самоцель |
| Интерфейс | FastAPI + Jinja2 + HTMX, локальный веб-UI | Одно приложение вместо двух проектов; переезд на Next.js возможен без переписывания бэкенда |
| База данных | PostgreSQL с pgvector, в Docker | JSONB для требований, векторный поиск, полнотекстовый поиск в одном месте |
| Развёртывание | Local-first, один профиль на инсталляцию | См. раздел 3 |
| Модель | Локальная через Ollama на хосте | Есть RTX 5080; приватность как свойство продукта |
| Эмбеддинги | `bge-m3` через Ollama, 1024 измерения | Сильнее на украинском, чем `paraphrase-multilingual-MiniLM` из плана; снимает зависимость от PyTorch и sentence-transformers на Windows |
| Абстракция над LLM | LangChain core | Заменяет связку LiteLLM + Instructor из плана: одна зависимость вместо трёх |
| Оркестрация | LangGraph | Состояние между попытками repair, ветвление, спаны в трейсе |
| Наблюдаемость | Langfuse, self-hosted, отдельным профилем compose | Бесплатно и без лимитов; данные не покидают машину. Выключен по умолчанию в `.env.example` |
| Хранение промптов | Файлы в git, не в Langfuse | Репозиторий остаётся самодостаточным; промпт проходит ревью как код |
| ORM и миграции | SQLAlchemy + Alembic | Как в плане |
| Лемматизация | pymorphy3 со словарями для украинского | BM25 без лемматизации на морфологичных языках почти бесполезен |

### Отклонения от исходного плана

1. **sentence-transformers → bge-m3 через Ollama.** Убирает PyTorch из зависимостей на
   Windows и даёт лучшее качество на украинском.
2. **LiteLLM + Instructor → LangChain core.** Три зависимости схлопываются в одну; structured
   output через `with_structured_output`.
3. **LangSmith → Langfuse.** LangSmith на бесплатном тарифе даёт 5 000 трейсов в месяц и
   14 дней хранения, self-hosting только на Enterprise. Langfuse self-hosted бесплатен и
   безлимитен. Слой трейсинга абстрактный — переключение возможно.
4. **Вакансии и скоры разнесены по таблицам.** В плане `match_score` и `application_status`
   лежали в таблице вакансий; это ломается при появлении второго профиля.
5. **Добавлено версионирование промптов и формулы скора в схеме БД.** В плане отсутствовало.

## 3. Модель развёртывания: local-first

Каждый пользователь запускает собственный экземпляр: `git clone`, `docker compose up`,
открывает `localhost:8000`. Аутентификации нет — изоляция обеспечивается тем, что это личная
машина пользователя.

В схеме БД при этом с первого дня присутствует `profile_id`, а рантайм использует один
профиль. Переход к переключателю нескольких локальных профилей — это один экран и фильтр в
запросах, без изменения схемы.

**Почему не мультипользовательский сервис с логином:**

- Локальная модель однопользовательская по природе — один GPU обслуживает один запрос.
  Хостинг для многих требует облачного LLM за счёт владельца сервиса.
- Хранение чужих резюме — это персональные данные со всеми вытекающими обязанностями.
- Объём работы до первой личной пользы примерно удваивается, при этом основная цель — понять,
  почему не отвечают конкретному человеку — не приближается.

Приватность в этой модели становится свойством продукта: резюме и история откликов не покидают
машину пользователя.

## 4. Архитектура

### Размещение процессов

```
Windows host
├── Ollama (нативно, CUDA) ─── RTX 5080
│     ├── модель извлечения и генерации
│     └── bge-m3 (эмбеддинги)
│
└── Docker
    ├── app    FastAPI + Jinja + HTMX     :8000
    ├── db     pgvector/pgvector:pg17     :5432
    │
    └── профиль "tracing" (отдельно):
        langfuse-web, langfuse-worker, langfuse-db,
        clickhouse, redis, minio
```

**Ollama остаётся на хосте.** Проброс GPU в контейнер на Windows идёт через цепочку
драйвер NVIDIA → шим WSL2 → NVIDIA Container Toolkit → контейнер, где каждое звено имеет
свою версию. Модели уже скачаны в `C:\Users\kir\.ollama`. Главное: при частых пересборках
контейнера приложения модель не выгружается из VRAM. Адрес задаётся переменной
`OLLAMA_BASE_URL`, поэтому позже можно добавить профиль `gpu` с контейнерным Ollama без
изменения кода.

**Langfuse — отдельным профилем compose.** `docker compose up` поднимает только приложение и
базу. `docker compose --profile tracing up` добавляет шесть контейнеров наблюдаемости
(Langfuse v4 требует ClickHouse, Redis и MinIO помимо web, worker и собственного Postgres).

### Модули и границы

| Модуль | Отвечает за | Не знает о |
|---|---|---|
| `parsers/` | HTTP-запросы и разбор HTML → DTO вакансии | БД, LLM |
| `ingest/` | дедупликация, upsert, пометка закрытых, журнал прогонов | HTML, LLM |
| `llm/` | подключение модели, реестр промптов, схемы вывода, трейсинг | БД, предметной области |
| `graphs/` | LangGraph-пайплайны, ретраи, repair | HTML, HTTP-роутах |
| `matching/` | BM25, косинусное сходство, гибридный скор, покрытие | LLM, БД, сети |
| `cv/` | чтение PDF и DOCX, банк тезисов | вакансиях |
| `profile/` | параметры поиска пользователя | парсинге |
| `web/` | роуты, шаблоны, HTMX-фрагменты | HTML вакансий, промптах |

Три границы несут основную нагрузку:

**Парсеры не знают о базе.** Принимают параметры поиска, возвращают список DTO. Следствие:
тестируются на сохранённых HTML-страницах без сети и без Postgres. При изменении вёрстки
падает конкретный тест на конкретном селекторе.

**Матчинг не знает ни о LLM, ни о базе.** Чистые функции: тезисы и требования на входе, число
и разбор покрытия на выходе. Формула скора будет меняться многократно, и каждое изменение
должно проверяться за секунды.

**Обращения к модели только в `llm/` и `graphs/`.** Единственная недетерминированная часть
системы заперта в двух модулях: мокается в одном месте, трейсится в одном месте.

### Поток данных

```
Онбординг:
  CV.pdf → cv/ → текст → graphs/parse_cv → тезисы → экран правки → БД

Сбор:
  профиль → parsers/ → DTO → ingest/ → vacancies
                                ↓ только новые и изменённые
                       graphs/extract_requirements → vacancy_requirements
                                ↓
                       Ollama bge-m3 → vacancy_embeddings (pgvector)

Скоринг:
  cv_theses + vacancy_requirements → matching/ → match_scores → таблица в UI
```

Извлечение требований и эмбеддинги считаются один раз на вакансию и кешируются. Пересчёт
скора после правки формулы или добавления тезисов не обращается к модели вообще — подбор
весов занимает секунды, а не минуты.

## 5. Модель данных

```
profiles
  id, name, target_roles[], locations[], remote_types[],
  stop_words[], languages[], created_at, updated_at

cv_theses
  id, profile_id → profiles
  text, category[], keywords[], metrics JSONB,
  strength, source_role,
  embedding VECTOR(1024),
  is_active, created_at, updated_at

vacancies                          -- объективные данные площадки
  id, source, external_id,
  title, company, url, description_raw, description_hash,
  location, salary_min, salary_max, salary_currency, remote_type,
  posted_at, first_seen_at, last_seen_at,
  missed_runs INT DEFAULT 0,
  is_active BOOLEAN DEFAULT true,
  created_at, updated_at
  UNIQUE(source, external_id)

vacancy_requirements
  id, vacancy_id → vacancies,
  hard_skills[], soft_skills[], must_have[], nice_to_have[],
  experience_years, domains[], language_reqs JSONB,
  prompt_version, model_name, extracted_at
  UNIQUE(vacancy_id, prompt_version)

vacancy_embeddings
  id, vacancy_id → vacancies,
  chunk_type, chunk_text, embedding VECTOR(1024), model_name, created_at
  -- chunk_type: 'requirement' — одно извлечённое требование (основной случай,
  --             используется в матрице покрытия)
  --             'description' — полный текст описания, один вектор на вакансию
  --             (используется для быстрого предварительного отсева)

match_scores                       -- субъективно: профиль × вакансия
  id, profile_id → profiles, vacancy_id → vacancies,
  bm25_score, semantic_score, hybrid_score,
  coverage JSONB, scorer_version, computed_at
  UNIQUE(profile_id, vacancy_id, scorer_version)

  -- структура coverage:
  -- {
  --   "items": [
  --     {"requirement": "Досвід управління IT-командою від 5 років",
  --      "kind": "must_have",          -- must_have | nice_to_have
  --      "similarity": 0.82,
  --      "verdict": "covered",         -- covered | partial | missing
  --      "best_thesis_id": "uuid"}     -- null при missing
  --   ],
  --   "counts": {"covered": 8, "partial": 2, "missing": 2}
  -- }

applications
  id, profile_id → profiles, vacancy_id → vacancies,
  status, applied_at, responded_at, notes, created_at, updated_at
  UNIQUE(profile_id, vacancy_id)
  -- status: new | applied | call | interview | offer | rejected | ignored

parse_runs
  id, source, query_params JSONB,
  started_at, finished_at,
  found_count, new_count, updated_count,
  status, error_text
```

### Ключевые решения схемы

**Разделение объективного и субъективного.** Текст вакансии одинаков для всех; скор и статус
отклика принадлежат профилю. Смешение этих сущностей в одной таблице, как в исходном плане,
потребует дублирования вакансий при появлении второго профиля.

**Версионирование в ключах уникальности.** `vacancy_requirements` уникальна по
`(vacancy_id, prompt_version)`, `match_scores` — по `(profile_id, vacancy_id, scorer_version)`.
Результаты старой и новой версии лежат рядом и сравниваются на реальных данных без пересчёта
базы. Это схемное отражение того, что работа над промптами — центральная активность проекта.

**Дедупликация и актуальность через счётчик.** Прогон нашёл вакансию — `missed_runs = 0` и
обновление `last_seen_at`. Не нашёл — `missed_runs += 1`. При достижении трёх —
`is_active = false`. Правило из плана «не найдена 3 прогона подряд» становится одним полем и
одним UPDATE.

**Отслеживание изменений через `description_hash`.** Совпал — ничего не делаем. Не совпал —
пишем новую версию требований и помечаем вакансию к перескорингу. Само по себе изменение
текста — сигнал для будущей аналитики.

**Чего нет в итерации 1:** `resume_versions`, `cover_letters`, `hypotheses`. Внешние ключи на
них заранее не закладываются — Alembic добавит колонки одной миграцией.

## 6. Извлечение требований

### Граф

```
      [normalize] ──► [extract] ──► [validate] ──┬── ok ──► [persist]
                          ▲                       │
                          └──── [repair] ◄────────┘ невалидно (макс. 2 попытки)
```

| Нода | Что делает |
|---|---|
| `normalize` | Чистит остатки разметки, определяет язык описания (uk/ru/en), обрезает до рабочего окна |
| `extract` | Вызов модели со structured output по Pydantic-схеме |
| `validate` | Формат плюс смысл: `must_have` не пустой; требование не попало одновременно в обязательные и желательные; извлечённые требования встречаются в исходном тексте |
| `repair` | Повторный вызов с точным указанием, что не так. Две попытки, затем вакансия помечается проблемной и попадает в очередь ручного разбора |

Проблемные вакансии не проглатываются молча — они видны в UI отдельным фильтром.

**О целесообразности LangGraph:** для одиночного извлечения обычной функции с ретраем хватило
бы. Граф окупается в цикле repair, где состояние протаскивается между попытками, и в
чат-интервьюере итерации 2. Дополнительно каждая нода становится отдельным спаном в трейсе.

## 7. Матчинг

### Три сигнала

**BM25 — буквальные совпадения.** Нужен потому, что ATS ищут точные слова, а не смыслы. Перед
индексацией текст лемматизируется через pymorphy3 со словарями для украинского: «керував» и
«керівництво» должны сводиться к одной лемме. Латиница (Syrve, SQL, ITIL) остаётся как есть.

**Семантика — гранулярно.** Сравнение целого текста CV с целым текстом вакансии даёт
усреднённую кашу, где одно сильное совпадение тонет в нерелевантных абзацах. Вместо этого
считается матрица «каждое требование против каждого тезиса»:

```
          тезис1  тезис2  тезис3
must_1     0.31    0.82    0.44   → max = 0.82  покрыто
must_2     0.22    0.19    0.61   → max = 0.61  частично
must_3     0.18    0.24    0.20   → max = 0.24  не покрыто
```

Максимум по строке — степень покрытия требования. Тезис-победитель показывается в UI: «это
требование закрывает вот такой твой тезис». Из этого напрямую строится экран gap-анализа.

### Формула

```
sim(r)         = max по всем активным тезисам от cos(emb(r), emb(t))
coverage_must  = среднее sim(r) по всем требованиям из must_have
coverage_nice  = среднее sim(r) по всем требованиям из nice_to_have
semantic       = 0.75 · coverage_must + 0.25 · coverage_nice
bm25_norm      = bm25 / (bm25 + k),  k = 8.0
hybrid         = 0.40 · bm25_norm + 0.60 · semantic
```

Пороги покрытия: `covered` при sim ≥ 0.75, `partial` при 0.55 ≤ sim < 0.75, `missing` при
sim < 0.55.

Уточнения, чтобы формула читалась однозначно:

- Требования внутри `must_have` считаются равнозначными — модель не возвращает их приоритет,
  и выдумывать веса не на чем. Разница в важности выражена только весами 0.75 / 0.25 между
  группами `must_have` и `nice_to_have`.
- Если `nice_to_have` пуст, `semantic = coverage_must`.
- `bm25_norm` нормализуется насыщающей функцией, а не min-max по выборке. Min-max сделал бы
  скор вакансии зависимым от того, какие ещё вакансии оказались в прогоне: одна и та же
  вакансия получала бы разные числа в разные дни. Константа `k` живёт в конфиге.

**Все константы — стартовые значения, а не истина.** Веса 0.4/0.6 взяты из исходного плана,
пороги — оценка на основе типичного поведения косинусных сходств у bge-m3. Они подлежат
калибровке на датасете `coverage` (см. раздел 9). Константы живут в конфиге, а не в коде;
`scorer_version` в БД позволяет сравнивать варианты без потери предыдущих результатов.

## 8. Слой промптов

**Источник истины — файлы в репозитории.**

```
prompts/
  extract_requirements/
    v1.yaml
    v2.yaml
  parse_cv/
    v1.yaml
```

Каждый файл содержит шаблон, few-shot примеры, ссылку на схему вывода и требования к модели.

Langfuse умеет хранить промпты у себя, и правка через UI без перезапуска удобна. Но тогда
репозиторий перестаёт быть самодостаточным — склонированный проект не работает без поднятого
Langfuse с залитыми промптами. И промпт перестаёт проходить ревью в коммите, хотя по влиянию
на поведение системы он равнозначен коду.

Решение: файлы в git, а Langfuse получает `prompt_version` в метаданных трейса и служит для
наблюдения и сравнения версий.

## 9. Оценка качества

### Датасеты

| Датасет | Размер | Что размечается вручную | Метрики |
|---|---|---|---|
| `requirements` | ~30 вакансий, поровну с work.ua и dou.ua | эталонные `must_have` и `nice_to_have` | precision и recall по must_have, доля выдуманных требований, доля валидного JSON с первой попытки, время, токены |
| `coverage` | ~20 пар вакансия-профиль | вердикт по каждому требованию: покрыто / частично / не покрыто | совпадение с ручным вердиктом — по нему калибруются пороги 0.75 и 0.55 |

### Прогон

```
python -m evals.run requirements --prompt-version v2
```

Результат отправляется в Langfuse как эксперимент и одновременно печатается локальным отчётом
в консоль — чтобы работа над промптами не зависела от поднятого трейсинга.

### Доля выдуманных требований

Метрика, на которой стоит настаивать отдельно. Модель охотно дописывает в требования то, чего
в вакансии не было, — например, добавляет «английский язык» просто потому, что он часто
встречается в IT-вакансиях. Для этой задачи это худший вид ошибки: кандидат начнёт подгонять
резюме под несуществующее требование. Проверяется механически — поиск извлечённого требования
в исходном тексте.

### Регрессия

Каждая вакансия, на которой обнаружена ошибка, добавляется в датасет. Через месяц в нём
накопятся реальные сложные случаи, и любое изменение промпта будет проверяться против них.

## 10. Тестирование

| Слой | Подход |
|---|---|
| `matching/` | Юнит-тесты. Чистые функции, без моков |
| `parsers/` | HTML-фикстуры — сохранённые реальные страницы с датой в имени файла. Без сети и БД |
| `ingest/` | Интеграционные, на настоящем Postgres в контейнере. Дедупликацию и `missed_runs` на моках проверять бессмысленно |
| `llm/`, `graphs/` | Контрактные тесты: сохранённые ответы модели, включая заведомо некорректные. Проверяется, что валидация ловит ошибку, а repair её чинит |
| `evals/` | Не в CI. Требуют GPU и недетерминированы. Запускаются вручную при изменении промптов |

Контрактные тесты отвечают на вопрос «код не падает», evaluations — «модель отвечает хорошо».
Смешивать их в одном прогоне означает получить красный CI, который начнут игнорировать.

## 13. Риски

| Риск | Митигация |
|---|---|
| Антибот-защита и рейт-лимиты площадок | Соблюдение `robots.txt`, паузы между запросами, честный `User-Agent`. При разработке парсера страницы кешируются на диск, чтобы не обращаться к живому сайту при каждой отладке. Собранные данные остаются локально и в репозиторий не попадают |
| Изменение вёрстки площадок | Парсер изолирован от остальной системы и покрыт тестами на фикстурах: ломается точечно и заметно |
| dou.ua может отдавать список через JavaScript | Playwright как альтернативный транспорт внутри того же `BaseParser`; остальная система разницы не заметит |
| Локальная модель слабо справляется с украинскими вакансиями | Величина неизвестна заранее, но измерима датасетом `requirements`. При неудовлетворительном качестве LangChain меняет провайдера настройкой: извлечение требований уходит на облачную модель, остальное остаётся локальным |
| Ресурсы: Langfuse v4 требует шесть контейнеров | Отдельный профиль compose — поднимается только когда нужен. Модель живёт в VRAM и с ним не конкурирует |
| Порог полезности данных для аналитики | Дашборд отложен в итерацию 2 сознательно: пока откликов меньше 20–30, выводы о паттернах недостоверны |
| Разрастание зависимостей экосистемы LangChain | Только `langchain-core`, `langgraph` и провайдерские пакеты; community-пакеты не берём. Промпты вынесены в отдельный слой, чтобы фреймворк оставался заменяемым |

## 14. Открытые вопросы к итерации 2

Не блокируют начало работ, решаются на данных итерации 1:

- Какая именно модель Ollama используется для извлечения — выбирается по результатам прогона
  датасета `requirements` на нескольких кандидатах
- Финальные веса гибридного скора и пороги покрытия — по датасету `coverage`
- Нужен ли чат-интервьюер в полном объёме или достаточно точечных уточняющих вопросов по
  слабым тезисам — станет ясно после работы с реальным gap-анализом
- Формат генерируемого резюме: WeasyPrint или Playwright
