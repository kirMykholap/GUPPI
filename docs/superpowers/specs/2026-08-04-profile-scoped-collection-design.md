# Дизайн: профильная видимость, теги ролей и нормализация полей

**Дата:** 2026-08-04
**Статус:** согласован, готов к написанию плана
**Предшественник:** `2026-08-03-job-hunt-ai-iteration-1-design.md` (план A — фундамент и сбор)

---

## 1. Зачем эта итерация

План A научил инструмент собирать вакансии и показывать их в таблице. Дальше
задумано превратить страницу «Вакансии» в полноценный инструмент поиска: фильтры
по городу и формату работы, теги предпочитаемых ролей переключателями, кнопка
запуска сбора, а над всем этим — выбор аккаунта, как выбор проекта в редакторе.

Строить это поверх текущей схемы нельзя. Три причины, каждая проверена по коду
или по живым данным:

**Фильтровать не по чему.** Признак удалённой работы у work.ua лежит в том же
поле, что и город: площадка пишет «Дистанційно» вместо названия города. Парсер
честно кладёт это в колонку `location`, но `remote_type` заполняет только
dou.ua. Фильтр «только удалённо» показал бы 4 вакансии из 11 фактически
удалённых.

**Второй профиль сломает первый.** `mark_missing` считает кандидатами «все
активные вакансии источника», без привязки к профилю. Профиль с другими тегами
засчитает пропуск чужим вакансиям и через три прогона их деактивирует.

**Схему дешевле менять сейчас.** В базе 55 записей. После накопления данных
любое из этих изменений превращается в миграцию с backfill'ом.

Разбиение всей задачи на три итерации согласовано отдельно:

| # | Итерация | Состав |
|---|---|---|
| **1** | **эта** | нормализация полей, профильная видимость, теги, два режима сбора, переход dou на HTML |
| 2a | «Вакансии» как инструмент | фильтры на странице, теги-переключатели, выбор профиля, пагинация — `2026-08-05-vacancies-as-a-tool-design.md` |
| 2b | Сбор из браузера | кнопка сбора, прогресс, плашка «условия изменились» — спека не написана |
| 3 | Оболочка | главная с выбором аккаунта, сайдбар инструментов, веб-формы профилей |

Итерация 2 разделена надвое при дизайне 2a (2026-08-05): запуск сбора из браузера
меняет модель выполнения и топологию контейнеров (сбор идёт с хоста, контейнер
`app` — только веб), а не разметку страницы, и требует собственной спеки.

## 2. Что входит и что не входит

**Входит:**

- разбор локации на город, признак «любой город» и формат работы; общий словарь значений для всех источников;
- отдельный модуль нормализации между парсерами и записью в БД;
- перевод dou.ua с RSS на HTML-выдачу с пагинацией;
- профильная видимость вакансий: `missed_runs`/`is_active` переезжают на пару «профиль ↔ вакансия»;
- теги ролей отдельной сущностью с состоянием вкл/выкл и связью «каким тегом найдена вакансия»;
- два режима сбора — суточная полная сверка и часовое быстрое обновление;
- рамка сбора в настройках профиля (города, только удалённо, глубина в днях);
- фильтры источников в URL, локальная перепроверка рамки в `ingest`;
- дробление транзакции по паре «источник + тег»;
- сохранение сигнала «описание изменилось»;
- разбор валюты (`грн` / `$` / `€`);
- CLI для профилей и тегов, миграция и команда переразбора.

**Не входит:**

| Что | Куда |
|---|---|
| фильтры и теги-переключатели на странице, кнопка сбора, плашка «условия изменились» | итерация 2 |
| главная с выбором аккаунта, сайдбар, веб-формы профилей | итерация 3 |
| схлопывание одной вакансии, найденной на двух площадках | отдельная итерация |
| матчинг с резюме, скоринг, `CREATE EXTENSION vector` | план B |
| глубина больше 30 дней у work.ua | площадка не отдаёт |

## 3. Разведка источников: факты, на которых стоит дизайн

Всё ниже проверено живыми запросами 2026-08-03/04, а не взято из документации.
Числа приведены, потому что от них зависят решения.

### 3.1 dou.ua: RSS непригоден

| Запрос | Отдал RSS | Есть на площадке |
|---|---|---|
| «Head of IT» | 6 | 6 |
| «менеджер» | **25** | **1401** |
| без поиска | 50 | — |

Фид отдаёт не более 25 элементов на поисковый запрос и 50 на общий, пагинации
нет: вакансии сверх лимита физически отсутствуют в ответе.

**Дефект действующего разбора.** Заголовок фида имеет вид
`Роль в Компанія, Зарплата, Місто, віддалено` — с переменным числом частей.
Текущая `parse_item_title` делит по последней запятой:

| Заголовок | Компания по текущему коду |
|---|---|
| `Head of IT в WayForPay, віддалено` | `WayForPay` ✓ |
| `Marketing manager в Антенор, $1000–3000, Київ, віддалено` | `Антенор, $1000–3000, Київ` ✗ |
| `Senior SMM… в FREITTY, $1000–2000, віддалено` | `FREITTY, $1000–2000` ✗ |

На любом запросе, где у вакансий указана зарплата, поле «компания» превращается
в мусор. В базе этого не видно только потому, что «IT Director» и «Head of IT»
дали простые заголовки. Переход на HTML устраняет причину, а не симптом.

### 3.2 dou.ua: HTML-выдача

Карточка отдаёт все нужные поля отдельными элементами:

```html
<li class="l-vacancy __hot">
  <div class="date">3 серпня</div>
  <div class="title">
    <a class="vt" href="…/vacancies/363911/?from=list_hot">Senior SMM Specialist</a>
    <strong>в <a class="company" href="…">FREITTY</a></strong>
    <span class="salary">$1000–2000</span>
    <span class="cities">віддалено</span>
  </div>
  <div class="sh-info">…сниппет описания…</div>
</li>
```

`h1` сообщает точное общее число: «1401 вакансія за запитом «менеджер»».

**Пагинация:** `POST /vacancies/xhr-load/` с `count` = уже загруженное смещение и
`csrfmiddlewaretoken` из cookie; ответ — JSON `{html, last, num}`, по 40 карточек.

**Порядок выдачи** (проверено на 305 карточках, 8 последовательных пачек):

```
первая страница:  20 карточек, все промо (__hot)
offset 20:        16 промо + 24 обычных | 3 серпня .. 3 серпня
offset 60:        40 обычных            | 3 серпня .. 3 серпня
offset 100:       40 обычных            | 3 серпня .. 31 липня
offset 140:       40 обычных            | 31 липня .. 30 липня
offset 180..300:  40 обычных            | монотонно вниз до 28 липня
```

Промо-блок кончается на ~36 карточках; дальше даты монотонно не возрастают.
Значит для dou **досрочная остановка по дате возможна**.

**Фильтры в URL** (числа — точный счётчик из `h1`):

```
менеджер                       1401
менеджер + remote               811
менеджер + city=Київ            690
менеджер + remote + exp=5plus   120
```

Фильтра по дате у dou нет.

### 3.3 work.ua: фильтры есть, порядок бесполезен

| Фильтр | Как передаётся | «менеджер», страниц |
|---|---|---|
| без фильтров | — | **944** (≈13 200 вакансий) |
| за 1 день | `?days=122` | 210 |
| за 7 днів | `?days=123` | 648 |
| за 14 днів | `?days=124` | 736 |
| за 30 днів | `?days=125` | 944 |
| удалённо | путь `/jobs-remote-{запрос}/` | 153 |
| город | путь `/jobs-kyiv-{запрос}/` | 314 (Київ), 68 (Львів) |
| рубрика / досвід / зарплата | `?category=`, `?experience=`, `?salaryfrom=` | 95 / 276 / 486 |

Фильтры складываются: `remote + days=122` даёт 33 страницы вместо 944.

**Порядок выдачи не по дате ни на какой глубине:**

```
стр. 1:  27.07 ×14
стр. 3:  22.07  03.08 ×13
стр. 8:  31.07 ×14
```

Причины две. Сверху идёт промо-блок, игнорирующий фильтры (в живой выдаче
класс `js-hot-block` стоит на **всех** карточках, тогда как в закоммиченной
фикстуре его нет ни на одной). И сортировка «За датою» — она же по умолчанию —
судя по всему, идёт по дате **обновления**, а в `title` карточки записана дата
**публикации**: работодатель поднимает старую вакансию, она уезжает вверх, дата
публикации не меняется. Это гипотеза, подтверждения на детальной странице найти
не удалось; проверить при реализации.

Практическое следствие: **досрочная остановка по дате для work.ua невозможна**,
и «искать до первой знакомой вакансии» тоже — свежее и старое перемешаны.

Ещё три наблюдения:

- «за 30 днів» = 944 = без фильтра: глубже 30 дней площадка в выдаче не показывает;
- запрос по умолчанию расширяется синонимами (`nosynonym=1` уменьшает выдачу с 944 до 744) — тег не является буквальным совпадением;
- `/jobs/?search=X` отвечает редиректом на `/jobs-X/`, то есть текущее построение URL стоит лишнего round-trip.

### 3.4 Объединять теги в один запрос нельзя

| Запрос | dou.ua | work.ua |
|---|---|---|
| `Head of IT` | 6 | 4 страницы |
| `IT Director` | 2 | 4 страницы |
| `Head of IT OR IT Director` | **0** | 1 страница, 10 карточек |
| `Head of IT\|IT Director` | **1** | 1 страница, 10 карточек |
| `"Head of IT" "IT Director"` | **1** | — |

Оба источника трактуют строку как одну фразу. Объединение не экономит запросы,
а теряет вакансии. **Один запрос на тег** — ограничение источников, не выбор.

### 3.5 Состояние базы на момент дизайна

55 вакансий (48 work.ua, 7 dou.ua), у всех `missed_runs = 0` и `is_active = true`.
Один профиль «Кирилл» с тегами «IT Director» и «Head of IT», `locations` пуст.
Одна строка в `applications`. Во всех 55 описаниях есть переносы строк — значит
все они пришли с детальных страниц, а не сниппетами.

Зарплата отсутствует у 39 из 55: у dou это наш пробел (RSS её не отдавал), у
work.ua — реальное отсутствие на площадке (в фикстуре блок зарплаты есть у 5
карточек из 14).

## 4. Схема данных

### 4.1 `profiles` — здесь живёт рамка сбора

| Поле | Тип | Смысл |
|---|---|---|
| `id`, `name` | — | без изменений |
| `collection_cities` | `text[]` | города для сбора; пусто = вся страна |
| `collection_remote_only` | `bool` | рамка «только удалённо» |
| `collection_depth_days` | `int`, по умолчанию 60 | глубина сбора |

Удаляются `target_roles` (переезжает в `profile_tags`), а также `remote_types`,
`stop_words`, `languages` — их не читает ни одна строка кода. План B заведёт то,
что ему понадобится, своей миграцией. `locations` становится `collection_cities`.

### 4.2 `profile_tags` — новая

`id`, `profile_id`, `text`, `is_enabled` (по умолчанию `true`), `created_at`.
Уникальность по `(profile_id, text)`.

Тег — отдельная строка с идентификатором, а не элемент массива: вакансии на него
ссылаются, а строковая ссылка ломается при первом переименовании.

### 4.3 `vacancies` — объективные данные площадки

| Изменение | Почему |
|---|---|
| убрать `missed_runs`, `is_active` | переезжают на пару «профиль ↔ вакансия» |
| `location` → `location_raw`, `city`, `city_any`, `work_format` | разбор локации; сырое значение хранится всегда |
| `+ description_is_full: bool` | описания качаются по требованию — надо знать, сниппет это или полный текст |
| `+ description_changed_at` | сигнал правки описания работодателем |
| `salary_currency` | суммы сохраняются только вместе с распознанной валютой |

`work_format`: `remote` | `hybrid` | `onsite` | `NULL`. `hybrid` заводится впрок —
ни один источник его сейчас не различает, но допустимое значение стоит ноль
работы, а расширение перечисления позже стоит миграции.

### 4.4 `profile_vacancies` — бывшая `applications`

Существующее: `profile_id`, `vacancy_id` (уникальны вместе), `status`,
`applied_at`, `responded_at`, `notes`.

Добавляется: `first_seen_at`, `last_seen_at`, `missed_checks` (int),
`last_missed_at` (защита «не чаще раза в сутки»), `is_active`.

Строка создаётся сборщиком при первой встрече, а не пользователем при смене
статуса. Статус `new` становится настоящим сохранённым значением, а не «строки
нет, значит `new`».

Расширение существующей таблицы вместо создания второй выбрано потому, что ключ
у них совпадает, а план B добавит на ту же пару скор матчинга. Иначе получилось
бы три таблицы на один ключ.

### 4.5 `profile_vacancy_tags` — новая связка

Ключ `(profile_vacancy_id, tag_id)`, обе ссылки с каскадным удалением.

Каскад даёт бесплатную обработку сирот: удалили тег — связки исчезли — у вакансии
не осталось тегов — она попадает в псевдо-фильтр «Найденные ранее».

### 4.6 `parse_runs` — журнал

Добавляется `profile_id`, `mode` (`full` / `quick`, у старых строк `NULL`) и
`total_available` — сколько источник заявил всего. Последнее нужно, чтобы
предупреждение о слишком широком теге и строка «собрано 300 из 13 216» были
основаны на факте. `query_params` (JSONB) хранит полный набор фильтров прогона.

### 4.7 Индексы

`vacancies.posted_at` (сортировка таблицы, сейчас индекса нет),
`profile_vacancies.profile_id`. Уникальность связки покрыта её первичным ключом.

### 4.8 Три оси состояния разведены

```
статус отклика        → profile_vacancies.status         (меняете вы)
состояние на площадке → profile_vacancies.is_active      (меняет полная сверка)
видимость по тегам    → есть ли включённый тег в связке  (меняют переключатели)
```

Они ортогональны и не могут смешаться, потому что лежат в разных местах.

## 5. Поток сбора

### 5.1 Два режима, и только один судит

| | `full` — суточная сверка | `quick` — часовое обновление |
|---|---|---|
| Что читает | всю выдачу по каждому включённому тегу в рамке профиля | только свежий срез |
| work.ua | без `days` (площадка и так отдаёт 30 дней) | `?days=122` |
| dou.ua | до рубежа `collection_depth_days` либо до `last=True` | первые `quick_batches` пачек (по умолчанию 3 ≈ 120 карточек) |
| Двигает счётчик пропусков | **да** | **никогда** |
| Пересобирает связки тегов | **да** | только добавляет |
| Стоимость, 5 узких тегов | ~30 запросов, ~1 мин | ~15 запросов, ~30 сек |

У dou нет фильтра по дате, поэтому `quick` берёт первые пачки приблизительно.
Это допустимо ровно потому, что `quick` никого не деактивирует и ничего не
отвязывает: его неполнота не может испортить состояние.

### 5.2 Порядок обхода

```
для каждого включённого тега:          ← теги снаружи
    для каждого источника:              ← источники внутри
        URL = тег + рамка профиля
        первый запрос → total_available
        обойти выдачу по режиму
        нормализовать → отобрать по рамке → upsert → связка с тегом
        записать parse_run
        COMMIT
```

Теги снаружи, источники внутри — потому что пауза в 2 секунды держится на хост:
ожидание work.ua накладывается на запрос к dou, и общее время падает почти вдвое.

Коммит после каждой пары решает известное ограничение плана A: сейчас весь прогон
— одна транзакция, и обрыв теряет и вакансии, и журнал, который объяснил бы, что
случилось. Заодно статус `running` в `parse_runs` становится наблюдаемым.

### 5.3 Отметка пропусков

Вызывается один раз на источник, **только в режиме `full`**, и только если все
запросы этого источника отработали и вернули полный набор id. Правило плана A
(пропуск считается по объединению всех запросов источника, а провал любого
запроса отменяет отметку для всего источника) сохраняется без изменений.

Кандидатом становится строка `profile_vacancies`, для которой верно всё:

1. вакансия этого источника, `is_active = true`;
2. связана хотя бы с одним тегом, **реально отработавшим** в этом прогоне;
3. попадает в текущую рамку сбора профиля;
4. с `last_missed_at` прошло не меньше 20 часов.

Условие 2: вакансия, найденная выключенным тегом, не судится никогда — мы по нему
не искали и не имеем оснований судить. Условие 3 закрывает сужение рамки:
поставили «только Київ» — львовские вакансии перестают быть кандидатами, а не
объявляются закрытыми. Условие 4 не даёт двум прогонам подряд сойти за двое суток.

Кандидат, которого не было в выдаче: `missed_checks += 1`, `last_missed_at = now`.
Достигло **2** — `is_active = false`.

Обратный ход бесплатный: `upsert` при встрече ставит `missed_checks = 0`,
`last_missed_at = NULL`, `is_active = true`.

### 5.4 Пересборка связок с тегами

**Полная сверка пересобирает связки того тега, по которому шла.** Тег отработал
полностью — вакансии, которых он не нашёл, теряют связку с ним. Быстрое
обновление связки только добавляет, никогда не убирает.

Правило симметрично отметке пропусков: право убирать имеет только полный проход,
видевший всю картину. Побочный эффект в ту же сторону: вакансия, которую
перестали находить все её теги, становится сиротой и уходит в «Найденные ранее»
— туда же, где вакансии удалённых тегов.

### 5.5 Широкий тег

Отдельного предохранителя не вводим: работает механизм плана A. Есть лимит
страниц; упёрлись — `ids_complete = false`, в журнале `ids_incomplete = true`,
отметка пропусков для источника пропускается, в выводе предупреждение.
Пользователь получает верхушку выдачи, и ничто не деактивируется по неполной
картине. `total_available` показывает, какую долю удалось забрать.

### 5.6 CLI этой итерации


## 6. Парсеры и нормализация

### 6.1 Конвейер

```
HttpClient            GET/POST, пауза, robots.txt, кеш — единственный выход в сеть
      ↓ HTML / JSON
Парсер источника      ТОЛЬКО извлечение: какой элемент что содержит
      ↓ list[RawVacancy] — сырые строки, как отдал сайт
Нормализация          общий модуль: строки → канонические значения
      ↓ list[VacancyDTO]
Ingest                отбор по рамке → upsert → связка с тегом
      ↓
mark_missing          только в режиме full
```

Разделение извлечения и нормализации даёт единый словарь значений на все
источники и делает так, что парсер физически не может его нарушить: он не
производит конечных значений. Нормализация — чистая функция без доступа к БД,
поэтому тестируется на строках, без фикстур.

### 6.2 Контракт парсера

```python
@dataclass(frozen=True)
class SearchFilters:
    cities: tuple[str, ...]   # пусто = вся страна
    remote_only: bool
    depth_days: int
    mode: Literal["full", "quick"]

parser.fetch_listings(query: str, filters: SearchFilters) -> ParseResult
```

`ParseResult`: `vacancies: list[RawVacancy]`, `truncated`, `ids_complete`,
`total_available: int | None`.

`SearchFilters` — значение, а не профиль: граница «парсеры не знают про БД и
профили» сохраняется и остаётся под проверкой разбором AST.

| Параметр | work.ua | dou.ua |
|---|---|---|
| `query` | путь `/jobs-{query}/` | `?search=` |
| `cities` | slug в пути; **slug неизвестен — не применяет** | `?city=Київ`, имя как есть |
| `remote_only` | `/jobs-remote-…/` | `?remote` |
| `depth_days` | **применить не может** — выдача не по дате | останавливает пагинацию |
| `mode` | `quick` → `?days=122` | `quick` → первые `quick_batches` пачек |

При создании парсер получает клиент и собственные предохранители:
`WorkUaParser(client, max_pages=25)`, `DouParser(client, max_batches=40,
quick_batches=3)`. `max_batches` — потолок полного обхода, `quick_batches` —
глубина быстрого режима; это разные числа и разные назначения.

### 6.3 Фильтры источника — оптимизация, истина — локальная проверка

`ingest` применяет всю рамку целиком — города, формат, дату — **независимо от
того, что парсер уже передал сайту**.

Обоснование прямо из разведки: промо-блок work.ua приходит мимо любых фильтров,
а сам фильтр `days` при первой проверке выглядел неработающим (сравнение шло по
первой странице, которую он не меняет). Ошибиться можно в обе стороны, и вторая
ошибка — счесть фильтр применённым, когда он молча не сработал — тихая. Двойная
проверка стоит одного условия на вакансию.

Отбрасывание считается и логируется. Когда парсер не смог применить фильтр
(неизвестный slug, отсутствие фильтра по дате), он пишет предупреждение — чтобы
медленный прогон имел объяснение.

### 6.4 work.ua

- URL строится как путь: `/jobs-{city_slug}-{запрос}/`, `/jobs-remote-{запрос}/`, `/jobs-{запрос}/` — это устраняет и лишний редирект с `/jobs/?search=`;
- `quick` добавляет `?days=122`;
- `total_available` — точное число из заголовка выдачи, при неудаче оценка «страниц × 14»;
- детальные страницы **убираются из сбора**: `max_details` исчезает, появляется отдельная `fetch_description(url)` по требованию;
- справочник slug'ов городов неполон; неизвестный slug → фильтр не применяется, отбор идёт локально, пишется предупреждение.

### 6.5 dou.ua — переписывается на HTML

RSS-парсер удаляется целиком вместе с `parse_item_title` и её дефектом.

| Поле | Откуда |
|---|---|
| дата | `div.date` |
| название + ссылка | `a.vt`, ссылка чистится от `?from=list_hot` |
| компания | `a.company` |
| зарплата | `span.salary` |
| город / формат | `span.cities` |
| сниппет | `div.sh-info` |

Пагинация: `POST /vacancies/xhr-load/`, `count` = смещение, csrf из cookie,
ответ `{html, last, num}`.

Остановка: промо-блок читается целиком (не упорядочен, но конечен, каждая
карточка проверяется по дате отдельно); дальше пачки по 40 до тех пор, пока
**вся пачка целиком** не окажется старше рубежа, либо до `last=True`. Остановка
по полной пачке, а не по первой старой карточке, — потому что монотонность дат
это наблюдение, а не гарантия площадки.

**Дата без года.** `div.date` содержит «3 серпня». Год выводится: если полученный
месяц больше текущего, это прошлый год. На стыке декабря и января ошибка здесь
стоит года разницы.

**HttpClient учится POST.** Сейчас у него только `get`. Нужны POST, cookie-jar и
csrf-токен, причём пауза между запросами, robots.txt и кеш обязаны действовать на
POST так же, как на GET: это единственная точка выхода в сеть.

### 6.6 Нормализация

```python
def normalize(raw: RawVacancy) -> VacancyDTO
```

| Из чего | Во что |
|---|---|
| «Дистанційно», «віддалено», «remote» | `work_format = remote`, `city = None` |
| «Вся Україна» | `city_any = True` |
| «Вишневе (Київська обл.)» | `city = "Вишневе"` |
| город | `city = город`, `work_format = onsite` |
| «80 000 – 120 000 грн» | `80000, 120000, UAH` |
| «$1000–2000» | `1000, 2000, USD` |
| «від 50 000 грн» | `50000, None, UAH` |
| «договірна» | всё `None` |
| «3 серпня» | дата с выведенным годом |
| «вакансія від 3 серпня 2026» | дата |

`location_raw` сохраняется всегда — если правило разбора окажется неверным,
переразобрать будет чем, без повторного обхода площадок.

Разбор зарплаты общий для источников: нормализация узких пробелов (`U+202F`,
`U+2009`, `U+00A0` — глазами неотличимы от обычного, поэтому задаются кодами),
«від»/«до» как отдельные слова, диапазон, валюта. **Если
валюту не распознали, суммы не сохраняются** — пустое поле честнее числа в
неизвестных единицах.

«Указан город → `onsite`» — сознательное упрощение: формально площадка говорит
«работа в Киеве», а не «в офисе». Но у work.ua «Дистанційно» стоит *вместо*
города именно потому, что это его собственный фильтр удалёнки. Альтернатива
(оставлять `NULL` везде, где источник не сказал явно) честнее, но бесполезнее:
фильтр «только офис» не нашёл бы ни одной вакансии.

### 6.7 Ingest

1. Отбрасывает вакансии вне рамки профиля, считает и логирует сколько.
2. `upsert` по `(source, external_id)`: новую вставляет, известную обновляет; при смене хеша описания ставит `description_changed_at`.
3. Создаёт или обновляет `profile_vacancies`: `last_seen_at`, сброс `missed_checks`, возврат `is_active`.
4. Добавляет связку «эта вакансия найдена этим тегом» — идемпотентно, вставкой с игнорированием конфликта.

**Сниппет никогда не затирает полное описание.** Описания качаются по требованию,
а сбор приносит только сниппет из карточки. Без этого правила первая же суточная
сверка перезаписала бы уже вытянутый полный текст коротким, сбросила бы
`description_is_full` и вдобавок подняла бы ложный сигнал «работодатель поправил
требования». Поэтому при `description_is_full = true` входящий сниппет
игнорируется целиком: ни текст, ни хеш, ни `description_changed_at` не трогаются.

Обратный переход — `fetch_description` подтянул полный текст поверх сниппета —
тоже **не** считается изменением описания: это наше уточнение, а не правка
работодателя.

**Принятое правило шире, чем «только полный → полный».** `description_changed_at`
ставится при любой смене сохранённого текста на другой текст того же уровня
полноты: полный на другой полный **и сниппет на другой сниппет**. Не ставится
только там, где сменился уровень полноты (сниппет поверх полного игнорируется
целиком, полный поверх сниппета — наше уточнение). Сниппет — то, что реально
приносит сбор сегодня (`fetch_description` в продакшен-коде не вызывается, см.
раздел 6 HANDOFF), поэтому формулировка «только полный сменился полным»
означала бы, что сигнал не поднимается никогда. Держится тестами
`tests/integration/test_upsert.py`.

Одна вакансия, найденная двумя тегами, — норма: строка в `vacancies` одна, строка
в `profile_vacancies` одна, связок две. Выключение одного тега оставит её видимой
по второму.

«Идентичная вакансия» здесь означает тот же источник и тот же id площадки. Одна
и та же вакансия на work.ua и на dou.ua останется двумя строками — схлопывание
между источниками вынесено в отдельную итерацию.

## 7. Миграция и backfill

### 7.1 Схема

Одна ревизия Alembic: изменения разделов 4.1–4.7.

### 7.2 Данные: миграция не нормализует

Миграция делает только механическое:

| Что | Как |
|---|---|
| `collection_cities` | из `locations` (сейчас пусто) |
| теги | по строке на каждый элемент `target_roles`, обе включены |
| `location_raw` | дословно из `location` |
| `description_is_full` | `true`, если в тексте есть перенос строки: сниппет собирался через `get_text(" ")` и переносов не содержит по построению. На текущих данных — 55 из 55 |
| `profile_vacancies` | строка на каждую из 55 вакансий; даты из вакансии; счётчики нули; существующая строка отклика сохраняет `status`, `applied_at`, `responded_at`, `notes` |
| связки | все 55 связываются с обоими тегами |

`city`, `city_any`, `work_format`, `salary_currency` миграция оставляет пустыми.

Причина: правила нормализации внутри миграции стали бы второй копией тех же
правил, а копии расходятся молча. Вместо этого — команда `jobhunt renormalize`,
перевычисляющая производные поля из `location_raw` **тем же модулем**, что и
обычный сбор. Запускается один раз после миграции и каждый раз, когда правило
разбора поправлено: перекрывать площадки заново не нужно.

Плюс первая полная сверка перезапишет эти поля у всех вакансий, которые ещё
висят на площадках.

Связывание всех 55 вакансий с обоими тегами — заведомое приближение: какой тег
какую нашёл, мы не знаем. Оно самоисправляется после первой суточной сверки по
правилу 5.4.

### 7.3 Обратимость

`location` удаляется только после копирования в `location_raw`. Удаление
`missed_runs`/`is_active` безопасно: на текущих данных это нули и `true`, они
переносятся в `profile_vacancies`. Существующий
`tests/integration/test_migrations.py` (отдельная БД, накат миграций, `alembic
check` с `compare_server_default`) должен остаться зелёным.

## 8. Тестирование

### 8.1 Границы под автоматической проверкой

| Граница | Как держится |
|---|---|
| `parsers/` не знает про БД, `ingest`, профили | разбор AST, как сейчас |
| **`normalize/` не знает про БД** | тот же разбор AST — новая проверка |
| сеть только через `http_client` | как сейчас, **включая POST** |
| миграции не расходятся с моделями | `alembic check` на отдельной БД |

### 8.2 Что покрывается

**Нормализация — на строках, без HTML.** Зарплаты: «договірна», «від 50 000 грн»,
«до 80 000 грн», диапазон, `$1000–2000`, `€`, неизвестная валюта → суммы не
сохраняются. Локации: «Дистанційно», «віддалено», «Вся Україна» → `city_any`,
«Вишневе (Київська обл.)». Даты: с годом, без года, отдельно стык декабря с
январём.

**Парсер dou.** Фикстуры: страница выдачи и ответ `xhr-load` (JSON). Извлечение
всех шести полей, чистка `?from=list_hot`, промо-блок читается целиком,
остановка срабатывает на полной пачке, `last=True` завершает обход, одна старая
карточка посреди свежих обход **не** обрывает.

**Парсер work.ua.** Новая фикстура **с промо-блоком** — текущая его не содержит,
а живая выдача состоит из него целиком. Построение URL: город-slug, `remote`,
`days=122` в быстром режиме. Неизвестный slug → фильтр не применяется, пишется
предупреждение, сбор продолжается. Разбор `total_available`.

**Ingest.** Карточка вне рамки отбрасывается и попадает в счётчик; повторный
прогон идемпотентен; связка тега не дублируется; `description_changed_at`
ставится при смене полного текста и только при ней. Отдельно: сниппет **не**
затирает полное описание и не поднимает сигнал изменения; подтягивание полного
текста поверх сниппета — тоже не изменение.

**Отметка пропусков — по одному условию на тест.** Вакансия выключенного тега не
судится. Вакансия вне рамки не судится. Два прогона в пределах 20 часов дают один
пропуск. Порог 2 деактивирует. Повторная встреча воскрешает и обнуляет счётчик.
Быстрый режим не двигает счётчик вообще.

**Пересборка связок.** Полная сверка снимает связку у ненайденных этим тегом;
быстрая не снимает никогда.

**Транзакции.** Коммит после каждой пары «источник + тег»; обрыв на середине
сохраняет всё закоммиченное вместе с журналом.

**Миграция.** `alembic check` плюс прогон backfill на слепке текущих 55 записей.

## 9. Решения и обоснования

Чтобы в следующей сессии не переигрывать заново.

**Расширяем `applications` вместо новой таблицы связи.** Ключ совпадает, план B
добавит на ту же пару скор матчинга — иначе получилось бы три таблицы на один
ключ. Цена: в одной таблице смешиваются объективное «профиль видел это в выдаче»
и субъективное «я откликнулся». Разделять их предполагается фильтром по статусу.

**`missed_runs`/`is_active` уходят с `vacancies` совсем, а не дублируются.**
«Вакансия закрыта площадкой» объективно узнать нельзя: ни один профиль не видит
всю биржу. Честная формулировка — «этот профиль перестал её находить», и она
профильная по определению.

**Порог деактивации — 2 полные сверки, не 3 прогона.** Счётчик прогонов меняет
смысл вместе с частотой запуска: при часовом сборе «3 прогона» это 3 часа.
Привязка к полной сверке плюс защита «не чаще раза в 20 часов» делает порог
честными двумя сутками независимо от того, сколько раз нажата кнопка.

**Одно состояние «неактивна», без промежуточного «выпала из выдачи».** work.ua не
показывает вакансии старше 30 дней, поэтому всё собранное неизбежно перестанет
находиться примерно на 31-й день. Различать это состояние сочтено лишним: порог в
60 дней — граница сбора, а не обязательство следить за вакансией 60 дней.
Ограничение записано как заметка (раздел 10).

**Досрочная остановка по дате — только у dou.** У work.ua выдача не упорядочена
по дате ни на какой глубине, и «искать до первой знакомой вакансии» пропустило бы
свежее, лежащее глубже. Ограничение объёма у work.ua достигается фильтрами
источника (`days`, город, `remote`), а не остановкой обхода.

**Описания не качаются при сборе.** Все поля, по которым идёт фильтрация, есть в
карточке выдачи. Качать сотни детальных страниц ради таблицы, которая будет
сужена до двух десятков строк, — плата вперёд за то, что почти наверняка не
понадобится. Разница на суточной сверке пяти тегов: ~1,5 минуты против ~10.

**Нормализация вынесена в отдельный модуль, а не оставлена в парсерах.** Словарь
значений обязан быть одним на все источники — это и есть «приведение типов»,
ради которого затевалась итерация. Отдельный этап делает нарушение
невозможным, а не маловероятным.

**Текстовый разбор описаний не вводится.** Локация, компания и дата не бывают
пустыми ни разу на 55 записях — оба источника заполняют эти слоты всегда. А цена
ошибки видна на нашей же фикстуре: строка «Віддалений доступ до корпоративних
систем» — это перк в списке условий, и любая регулярка на «віддален» пометила бы
такую вакансию удалённой вопреки честному значению поля. Общее правило:
структурное поле важнее текста; к тексту обращаемся, только если структурного
поля у источника нет вовсе, и только по якорю.

## 10. Известные ограничения

| Что | Последствие | Статус |
|---|---|---|
| work.ua не отдаёт вакансии старше 30 дней | `collection_depth_days` больше 30 для этого источника не действует | заметка, принято |
| Порядок выдачи work.ua, предположительно, по дате обновления | гипотеза без подтверждения; проверить при реализации | открыто |
| В живой выдаче work.ua все карточки помечены `js-hot-block`, в фикстуре — ни одна | фикстура может описывать разметку, которой уже нет | закрывается новой фикстурой |
| Монотонность дат в обычном блоке dou | наблюдение на 305 карточках, не гарантия площадки | остановка по полной пачке |
| Запрос work.ua расширяется синонимами | тег не является буквальным совпадением | принято, повышает полноту |

| Одна вакансия на двух площадках = две строки | в таблице будут видны дубли | отдельная итерация |
| Связки тегов при backfill — приближение | самоисправляется после первой полной сверки | принято |

## 11. Требование к плану реализации

HANDOFF фиксирует урок плана A: семь дефектов из тринадцати были одного класса —
молча проглоченный сбой, — и почти все переехали в код прямо из примеров в плане,
хотя сам план это запрещал в разделе ограничений.

Поэтому в плане этой итерации **каждый пример кода, где возможна частичная
деградация**, пишется сразу с логированием этой деградации:

- неизвестный slug города;
- неразобранная карточка выдачи;
- недоступная детальная страница;
- фильтр, который парсер не смог применить;
- вакансия, отброшенная как не попавшая в рамку;
- пачка dou, оборвавшая обход по рубежу.

Не «ревью поймает», а изначально.
