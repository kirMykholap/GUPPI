**Дата:** 2026-08-05
**Предшественник:** `2026-08-04-profile-scoped-collection-design.md` (слайс 1)
**Статус:** утверждён владельцем, план реализации ещё не написан

## 1. Зачем этот слайс

Слайс 1 научил инструмент собирать вакансии профильно: рамка сбора, теги ролей,
два режима, честная нормализация полей. Но управлять всем этим можно только из
терминала, а страница `/vacancies` показывает один плоский список, в котором
смешаны вакансии живых тегов, вакансии выключенных тегов и сироты — вакансии,
чей тег удалили.

Этот слайс делает страницу рабочим местом: показывать по умолчанию то, что
сейчас ищется и висит на площадке; уметь сузить список любым признаком, который
уже есть в данных; переключать теги мышью; листать список, не загружая его
целиком.

Слайс закрывает четыре ограничения из раздела 6 передачи состояния:
выключенный тег не прячет свои вакансии; сироты висят в общем списке; фильтр по
статусу считается в Python после загрузки всех строк; веб жёстко прибит к самому
раннему профилю.

## 2. Что входит и что не входит

Роадмап слайса 1 называл итерацию 2 одной строкой: «фильтры на странице,
теги-переключатели, запуск сбора из браузера с прогрессом». При разборе объёма
последний пункт оказался другой природы — он меняет модель выполнения и
топологию контейнеров, а не разметку. Поэтому итерация 2 разделена надвое, и
**эта спека описывает только 2a**.

| Входит (2a) | Не входит |
|---|---|
| состав списка по умолчанию и три переключателя расширения | запуск сбора из браузера и прогресс — спека 2b, см. раздел 12 |
| фильтры: город, формат работы, поиск по тексту, «только с зарплатой» (плюс существующие статус и источник) | плашка «условия изменились» — 2b |
| чипы тегов как фильтр показа | веб-формы профиля и рамки сбора — слайс 3 |
| переключение `is_enabled` тега из браузера | добавление и удаление тегов из браузера — остаётся в CLI, см. раздел 10 |
| выбор профиля | главная, сайдбар, выбор аккаунта — слайс 3 |
| пагинация «показать ещё» | схлопывание одной вакансии с двух площадок — отдельная итерация |
| разделение веб-слоя на роуты и доступ к данным | матчинг с резюме — план B |

## 3. Состояние на момент дизайна

Факты по коду, на которых стоит дизайн:

- `list_vacancies` (`web/routes/vacancies.py`) тянет **все** строки профиля и
  отбрасывает несовпавшие по статусу уже в Python (`continue` в цикле). Фильтры
  по источнику и активности при этом в SQL;
- фильтры на странице — обычная GET-форма с `onchange="this.form.submit()"`:
  каждый клик перезагружает страницу целиком;
- htmx подключён и работает: смена статуса возвращает фрагмент ячейки
  (`_status_cell.html`), в `base.html` есть глобальный обработчик
  `htmx:responseError`, подставляющий тело ответа при 4xx;
- `vacancies_page` и `change_status` берут `Profile` первым по `created_at` —
  второй профиль в вебе недостижим;
- `ProfileTag.is_enabled` есть в схеме и уже управляет сбором (`run_profile`
  отбирает только включённые) и отметкой пропусков (`mark_missing` судит только
  пары, связанные с тегом, реально отработавшим в прогоне). Выдачу `/vacancies`
  он не фильтрует — об этом прямо написано в докстринге модели;
- `ProfileVacancyTag` каскадно удаляется с обеих сторон: удалили тег — связки
  исчезли, вакансия стала сиротой. Псевдо-фильтр «Найденные ранее» в докстринге
  назван будущей работой;
- индексы, которые уже есть и пригодятся: `ix_profile_vacancies_profile_id`,
  `profile_vacancies.status`, `profile_vacancies.is_active`,
  `ix_vacancies_posted_at`, `vacancies.source`,
  `ix_profile_vacancy_tags_tag_id`;
- размер данных сегодня: 57 вакансий у одного профиля. Порядок, к которому
  готовимся, — тысячи.

## 4. Поведение страницы

### 4.1 Состав списка по умолчанию

По умолчанию таблица показывает пары «профиль ↔ вакансия», для которых верно всё:

1. пара активна (`is_active = true`);
2. есть связка хотя бы с одним **включённым** тегом.

Список по умолчанию отвечает на один вопрос: «что сейчас ищется и висит на
площадке». Всё остальное — за переключателями, каждый независимо расширяет
выборку:

| Переключатель | Что добавляет |
|---|---|
| показывать неактивные | пары, которые профиль перестал находить (`is_active = false`) |
| вакансии выключенных тегов | пары, у которых связки есть, но все — с выключенными тегами |
| найденные ранее | сироты: пары без единой связки (тег удалён) |

«Найденные ранее» — та самая формулировка из докстринга `ProfileVacancyTag`.
Сирота не деактивируется никогда (её некому судить), поэтому без этого
переключателя она из списка по умолчанию исчезает навсегда — это осознанно:
работа не потеряна, она за одним кликом.

### 4.2 Фильтры

| Фильтр | Как работает |
|---|---|
| статус | как сейчас, но условием в SQL |
| источник | как сейчас |
| город | выпадающий список из городов, реально встречающихся у этого профиля |
| формат работы | офис / удалёнка / «вся Україна» (`work_format`, `city_any`) |
| только с зарплатой | `salary_min IS NOT NULL` |
| поиск по тексту | подстрока в заголовке или компании, без учёта регистра |

Фильтра по сумме зарплаты нет намеренно: валюты разные (UAH/USD/EUR), курса в
проекте нет, сравнение чисел разных валют вводило бы в заблуждение. Фильтра
«свежее N дней» нет по той же причине честности: колонка — дата **обновления**
карточки площадкой, а не первой публикации (установлено живой проверкой слайса 1),
и фильтр «за 7 дней» читался бы как «опубликовано недавно».

### 4.3 Теги: два разных органа управления

Это главное различение слайса, и оно должно быть видно в интерфейсе.

**Чипы тегов над таблицей — фильтр показа.** Мультивыбор по «или»: показать
вакансии, найденные любым из выбранных тегов. Живут в адресной строке, БД не
трогают, на сбор не влияют.

**Переключатель «искать по этому тегу» в списке тегов — меняет `is_enabled`.**
Влияет на следующий сбор и на отметку пропусков. Рядом с ним прямо написано, что
на текущий список это не влияет: иначе пользователь ждёт исчезновения строк и не
понимает, почему их нет.

Взаимодействие чипов с переключателями видимости: **если выбран хотя бы один
чип, условие по тегам заменяется целиком на «связана с одним из выбранных»**, а
три переключателя из 4.1 к тегам больше не применяются (переключатель
«показывать неактивные» продолжает работать). Без этого правила выбор чипа
выключенного тега давал бы пустой список — формально верно, по смыслу абсурдно.

### 4.4 Пагинация

«Показать ещё» по 50 строк, вставка в конец таблицы. Номерных страниц нет:
просмотр списка — занятие «скроллить и смотреть», а не «перейти на страницу 7».

Кнопка появляется, только когда есть что показывать: запрашиваем 51 строку,
показываем 50, лишняя отвечает на вопрос «есть ли ещё» без отдельного `COUNT(*)`.

### 4.5 Профиль

Селектор в шапке. При единственном профиле не показывается — выбирать не из чего.

Порядок разрешения: `?profile=<uuid>` из адреса → cookie последнего выбранного →
самый ранний по `created_at` (текущее поведение). Явный выбор пишет cookie.

## 5. Данные и запросы

### 5.1 Один запрос, вся фильтрация в SQL

Все условия раздела 4 складываются в один `SELECT` через `AND`. Ни одно
не выполняется после выборки. Это прямо чинит текущий дефект: сегодня ради
показа 50 строк из базы приезжают все.

Теги для показанных строк догружаются вторым запросом на всю страницу
(существующий `_tags_by_pair`) — это не N+1 и переносится как есть.

### 5.2 Три состояния тега — одним и тем же `EXISTS`

```
EXISTS_enabled = EXISTS (связка пары с тегом, у которого is_enabled = true)
EXISTS_any     = EXISTS (связка пары с любым тегом)
```

| Что показываем | Условие |
|---|---|
| по умолчанию | `EXISTS_enabled` |
| + вакансии выключенных тегов | `EXISTS_any` |
| + найденные ранее | `EXISTS_enabled OR NOT EXISTS_any` |
| оба переключателя | условия по тегам нет вовсе |
| выбраны чипы | `EXISTS (связка с тегом из выбранных)` |

Таблица — часть контракта: каждая строка проверяется отдельным тестом.

### 5.3 Порядок и пачки

Сортировка получает третий ключ: `posted_at DESC NULLS LAST, first_seen_at DESC,
id`. Первые два не задают полного порядка — у большинства вакансий дата
совпадает с точностью до дня, — и без `id` две строки могут поменяться местами
между запросами пачек, из-за чего одна продублируется, а другая пропадёт.

Пагинация по `OFFSET`. Ограничение честно называем: если между запросами пачек в
базу приедут новые вакансии, границы сдвинутся. В этом слайсе сбор из браузера
не запускается, а фоновый сбор идёт по расписанию пользователя, так что
вероятность низкая, цена — одна дублирующаяся строка. Keyset-пагинация здесь не
окупается.

### 5.4 Значения для выпадающих списков

Города и источники считаются из данных **этого** профиля (`SELECT DISTINCT`), а
не задаются константой: список городов, в котором половина пунктов ничего не
находит, хуже короткого. Источники сегодня константа в шаблоне — переезжают
туда же.

### 5.5 Индексы

Новых индексов слайс не добавляет. Существующих хватает на порядок «тысячи
строк», а добавлять индекс без замера — гадание. Если замер (раздел 7) покажет
обратное, индекс заводится отдельной задачей с миграцией и с числом до/после.

Отдельно про поиск по тексту: `ILIKE '%…%'` индексом не ускоряется в принципе
(нужен триграммный индекс и расширение `pg_trgm`). На тысячах строк
последовательное сканирование по двум текстовым колонкам — единицы миллисекунд.
Расширение не заводим.

## 6. Структура кода и границы

`web/routes/vacancies.py` — 306 строк, и в нём сегодня и сборка запросов, и
рендер, и правила статусов отклика. Слайс добавляет шесть фильтров, теги,
пагинацию и профиль; без разделения файл удваивается.

```
src/jobhunt/web/
├── data/                    доступ к БД: единственное место со SQL в веб-слое
│   ├── vacancies.py         фильтры -> запрос, выборка строк, запись статуса
│   │                        (сюда переезжают list_vacancies и set_status)
│   ├── tags.py              теги профиля, переключение is_enabled
│   └── profiles.py          список профилей, разрешение выбранного
├── routes/
│   ├── vacancies.py         обработчики: страница, фрагмент строк, POST статуса
│   └── tags.py              обработчики: список тегов и переключатель
└── templates/
    ├── vacancies.html       каркас страницы
    ├── _filters.html        форма фильтров
    ├── _tag_chips.html      чипы тегов
    ├── _rows.html           строки + кнопка «показать ещё»
    └── _status_cell.html    существует
```

Разбор query-параметров в объект фильтров живёт в `data/vacancies.py` и
используется обоими роутами (страницей и фрагментом) — иначе страница и её
фрагмент разойдутся в понимании одних и тех же параметров.

**Новая граница под AST-тестом:** ни один модуль `web/routes/` не обращается к
БД напрямую — ни `select(`, ни `session.execute(`. По образцу четырёх границ,
которые уже держатся тестами (`parsers`/`normalize`, сеть, запись вакансий).
Граница проверяется на синтетическом источнике, а не только прогоном по
заведомо чистым файлам — урок ре-ревью слайса 1.

## 7. Взаимодействие: htmx, адресная строка, отклик

Роут `GET /vacancies/rows` возвращает фрагмент строк — то же, что страница
рендерит внутри `<tbody>`, плюс кнопка «показать ещё».

- фильтры и чипы: `hx-get` на этот роут, `hx-target="#rows"`,
  `hx-swap="innerHTML"`. Адрес отражает состояние, ссылку можно сохранить и
  открыть заново — но **заголовком `HX-Push-Url` от роута фрагмента, а не
  атрибутом `hx-push-url`** (см. поправку ниже);
- поиск по тексту: `hx-trigger="keyup changed delay:250ms, search"` — без
  задержки запрос уходил бы на каждую букву. Триггер самой формы при этом
  обязан называть свои источники (`from:(#filters select, #filters
  input[type=checkbox])`), а не ловить всплывший `change`: иначе поле поиска
  на потере фокуса шлёт второй запрос вдогонку отложенному;
- «показать ещё»: тот же роут с `offset`, **без** записи адреса — иначе в нём
  останется `offset=50`, и открытая заново страница покажет вторую пачку вместо
  первой. Подменяется `hx-swap="outerHTML"` строка самой кнопки (`#more-row`), а
  не `beforeend` в `#rows`: кнопка едет вместе с новой пачкой и на последней
  пачке просто не приезжает;
- переключатель тега (`is_enabled`): `hx-post` на роут тегов, ответ — обновлённый
  фрагмент списка тегов. Таблица при этом не меняется (см. 4.3).

**Поправка 2026-08-05 (по итогам слайса).** Два места этого раздела расходились
с кодом, и одно из них было прямой причиной Critical.

`hx-push-url="true"` кладёт в адрес **фактический URL запроса**, то есть
`/vacancies/rows?…`. Сохранённая ссылка после первой же смены фильтра вела на
фрагмент и отдавала голый набор `<tr>` без страницы вокруг. Адрес пушится
заголовком `HX-Push-Url` из роута фрагмента — и только при `offset=0`;
обоснование записано в докстринге `vacancy_rows`, читать его перед добавлением
любого нового роута, который пушит адрес. Мёртвые атрибуты из шаблонов убраны, а
не оставлены: ветка, вернувшая 200 без заголовка, молча воскресила бы дефект.
Отдельный guard уводит редиректом адрес фрагмента, открытый как страница, —
заголовок не отменяет ссылок, уже разошедшихся по закладкам.

`hx-swap="beforeend"` для «показать ещё» описывал не то, что делает код, с самой
задачи 3. Прав код: пачка приезжает вместе со своей кнопкой, поэтому подменяется
строка кнопки целиком.

**Замер отклика — первая задача слайса, а не последняя.** После того как готовы
запрос и фрагмент, измеряется реальное время ответа `/vacancies/rows` на боевой
БД и записывается в план числом. Ориентир: ниже ~100 мс отклик воспринимается
как мгновенный, и тогда клиентская фильтрация не нужна вовсе. Если замер даст
больше — меры принимаются точечно (индекс по конкретной колонке, скрытие строк
на клиенте до ответа) и только там, где число это оправдывает.

## 8. Ошибки и краевые случаи

| Случай | Поведение |
|---|---|
| профиля нет вовсе | текущее сообщение с командой создания профиля |
| профиль из URL не существует | явное сообщение и возврат к выбору, а не молчаливый показ чужого списка |
| пусто по фильтрам | «ничего не найдено» + кнопка сброса; отличается от «вакансий нет вовсе», где предлагается запустить сбор |
| все теги выключены | сообщение «все теги выключены», а не пустая таблица без объяснения |
| смена статуса в отфильтрованном списке | строка остаётся на месте до следующего запроса, даже если перестала подходить под фильтр — иначе она исчезает под курсором в момент клика |
| отказ сервера на htmx-запросе | существующий обработчик `htmx:responseError` подставляет фрагмент с сообщением |
| `offset` за пределами выборки | пустой фрагмент без кнопки, а не ошибка |

## 9. Тестирование

**Запросы (интеграционные, на своих данных):**

- каждый фильтр раздела 4.2 — отдельным тестом;
- сочетание двух фильтров — условия складываются через `AND`, а не затирают друг
  друга;
- все пять строк таблицы 5.2 — по тесту на каждую: три состояния тега (живой,
  выключенный, сирота) в каждом сочетании переключателей;
- граница пачки: 51 строка при размере 50 — кнопка есть; ровно 50 — кнопки нет;
- стабильность порядка: две вакансии с одинаковым `posted_at` не дублируются и
  не пропадают между первой и второй пачкой;
- два профиля: списки не пересекаются; выбор из URL уважается; cookie-фолбэк
  работает; несуществующий профиль в URL даёт сообщение.

**Роуты:** страница и фрагмент отвечают 200; фрагмент возвращает только строки, а
не целую страницу; переключение `is_enabled` меняет БД и возвращает обновлённый
фрагмент списка тегов.

**Граница:** AST-тест «роуты не обращаются к БД» — с проверкой на синтетическом
источнике, что он ловит и `select(`, и `session.execute(`.

**Живая проверка в браузере — отдельным шагом в конце плана.** В слайсе 1 ровно
этот шаг остался незакрытым хвостом, потому что стоял последним пунктом
последней задачи. Здесь он оформляется как задача с перечнем сценариев: клик по
чипу, «показать ещё», переключение тега, смена профиля, поиск с задержкой, путь
ошибки.

## 10. Решения и обоснования

**Почему htmx, а не React.** React потребовал бы узел сборки в проекте, где
сейчас только Python и `uv`, JSON-слой поверх уже готовых запросов, клиентское
состояние и вторую тест-культуру (всё качество проекта держится на pytest и
AST-границах). Взамен дал бы то, чего здесь нет: сотни компонентов и сложные
клиентские взаимодействия. Задача — одна таблица в локальном приложении для
одного пользователя. Если слайс 3 («оболочка») вырастет во что-то заметно
большее, решение пересматривается — но под реальную потребность, а не заранее.

**Почему чипы не совмещены с `is_enabled`.** У них разные последствия: чип — «не
показывай сейчас», переключатель — «не ищи впредь». Совмещение означало бы, что
«убрать с глаз на минуту» останавливает сбор по этой роли, а вернуть его можно
только вспомнив, что ты нажал.

**Почему сироты скрыты по умолчанию, а не помечены.** Сирота не деактивируется
никогда: `mark_missing` судит только пары, связанные с отработавшим тегом. То
есть в общем списке она копится безвозвратно. Пометка сделала бы список честнее,
но не короче.

**Почему 51 строка вместо `COUNT(*)`.** Точное число строк на странице не
показывается, а нужен только ответ «есть ли ещё» — отдельный агрегатный запрос
ради него не нужен.

**Почему `id` в сортировке.** Без полного порядка `OFFSET` не гарантирует
устойчивости пачек. У большинства вакансий `posted_at` — один и тот же день, то
есть вырожденный случай здесь не редкость, а норма.

**Почему cookie, а не только URL, для профиля.** Открытие `/vacancies` без
параметров — обычный путь (закладка, ввод адреса). Без cookie он всегда
приводил бы к самому раннему профилю, и второй профиль требовал бы каждый раз
искать ссылку.

## 11. Известные ограничения, которые слайс не закрывает

| Что | Почему |
|---|---|
| статусы отклика остаются английскими идентификаторами (`new`, `applied`) | косметика; трогать словарь статусов заодно с фильтрами — лишний риск в том же дифе |
| `stats.new` объективен, а не профилен | относится к сбору, не к странице |
| пустая выдача work.ua глушит деактивацию источника | дефект парсера, ждёт фикстуры «нічого не знайдено» |
| зарплату нечем переразобрать (`salary_raw` не хранится) | план B, требует миграции |
| `Profile.name` не уникален в схеме | защита в CLI есть; веб адресует профиль по `id`, поэтому дубль имени страницу не путает |

## 12. Следующий слайс — 2b: сбор из браузера

Оставшийся пункт итерации 2. Записан здесь, чтобы следующая сессия начинала не с
чистого листа. **Своей спеки ещё нет — её надо написать до кода.**

Что уже известно и что придётся решить:

- **Сеть из контейнера.** Сегодня `parse` выполняется с хоста, а контейнер `app`
  — только веб-интерфейс (README). Сбор из браузера означает, что в интернет
  ходит контейнер: robots.txt, паузы между запросами к хосту, дисковый кеш и
  права — всё оттуда. Либо остаётся вариант «веб ставит задачу, исполняет
  хост» — это другая архитектура, и выбор между ними и есть первый вопрос спеки.
- **Фоновое выполнение.** `run_profile` синхронный и идёт минуты (живая проверка
  слайса 1: широкий тег отдал 350 записей, упершись в лимит 25 страниц).
  HTTP-запрос этого не переживёт; нужна фоновая задача, переживающая перезапуск
  контейнера, и решение, что делать с прогоном, начатым и брошенным.
- **Наблюдаемый прогресс.** Статус `running` в журнале сегодня не наблюдаем:
  вставка записи и её финализация идут в одной транзакции (раздел 6 передачи
  состояния). Прогресс в браузере начинается с починки этого, а не с рисования
  полоски.
- **Защита от параллельных запусков** одного профиля и от ухода со страницы во
  время сбора.
- **Плашка «условия изменились»** — сюда же: она сообщает, что рамка или теги
  поменялись после последнего сбора, и предлагает пересобрать.

## 13. Требование к плану реализации

План обязан:

1. начинаться с задачи «запрос в SQL + фрагмент строк + **замер** отклика», и
   число из замера должно попасть в план — от него зависит, нужна ли клиентская
   часть вовсе;
2. вести разделение `web/` на `data/` и `routes/` отдельной задачей **до** того,
   как в файлы поедет новая логика, — иначе разделение придётся делать на вдвое
   большем файле;
3. закрывать таблицу 5.2 тестами построчно: пять сочетаний, каждое — своим
   набором данных;
4. заканчиваться задачей живой проверки в браузере с перечнем сценариев из
   раздела 9, а не пунктом внутри последней задачи.
