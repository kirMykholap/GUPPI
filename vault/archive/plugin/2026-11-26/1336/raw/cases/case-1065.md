## Case 1065 — The number of a changed Case is checked once, with its exception

> **context:**
> `estimate-case-build-settles-form-by-itself` checks how `case-guppi` settles a choice of form. One line of its Criterion also says that `case-guppi`, asked by a message or by a finding of `/pre-spec` to change a Case, builds the change under the number of that Case. That line has no exception. But the Splitting section of `vault/wiki/case-schema.md`, and the check of the case file, set a new number for a Case that has a decision line in the session's ledger and comes back in another shape, with `{supersedes:case N}` marks. The Render of `rule-case-build` holds that exception: a Case keeps its number outside Work Mode unless `case-schema.md` sets a new one for it (case 870). The reading at the `/hi` of this session, line 2 of the session's ledger, set the Estimate `failed` on that line alone. In session 2003, Case 1060 was sent the findings of `/pre-spec` and came back with sub-cases. Its `case-guppi` first built it as Case 1062 with a supersedes mark on case 1060 (transcript `agent-a282ffe194ed92d85.jsonl` L378). The main agent then sent it back under 1060, and the agent rebuilt it under 1060 with no marks (L425). The check refused that build and named 1063 in its output (L426), and the agent quoted that refusal in its `**Fact:**` reply (L430), the line that line 2 of the session's ledger cites. The main agent then wrote that its message was wrong (L431). The agent built 1063 with `{supersedes:case 1060}` (L450), and the ledger of session 2003 holds those lines. So the agent followed `case-schema.md`, and the Criterion is wrong. The rule of the number is already in the Criterion of `estimate-case-build-writes-the-case`, with the exception: it says that a Case keeps its number outside Work Mode unless `case-schema.md` sets a new one for it. That Estimate is `passed`. So this Case drops the line from `estimate-case-build-settles-form-by-itself` and does not write the exception there a second time, since `case-schema.md` sets that nothing is signed twice or in two wordings. That is a choice of form, and the line of `estimate-case-build-writes-the-case` that points to this Estimate for how a change is built still holds: this Estimate still checks where a fix goes that adds a second behaviour, and the new Case beside a ratified one. The `purpose` loses the same clause. The first part of the `method` reads a new Render in the Spec, and this Case writes no new Render, so the `method` reads the live `.claude/agents/case-guppi.md` at Retro instead. The Render of `rule-case-build` already states the exception, so it does not change. The main agent sent the Case back under its old number, and that is the Frontier item C2 (`orchestration.md`), which is not built yet; this Case does not change `orchestration.md`. A Grep for `estimate-case-build-settles-form-by-itself` over `{vault/wiki,.claude,.guppi}/**` printed four files: `brief.md`, `log.md`, `rule-case-build.md` (its `estimates` list) and `estimate-case-build-writes-the-case.md`. No test of `.guppi/tests/` names the page. The session's ledger holds no `error` lesson, so no `{addresses:...}` mark is set.

> **problem:**
> The Criterion of `estimate-case-build-settles-form-by-itself` says that a change is always built under the number of its Case. `case-schema.md` sets a new number for a ratified Case that comes back in another shape. So a correct build reads as `failed`.

> **then:**
> A choice of form is how the work splits into Cases and sub-cases, whether a promise takes a new Estimate, a replaced Criterion or an Estimate that already checks the change, which page holds a thing, and where a fix goes that adds a second behaviour to a ratified Case.
> **＋** It settles a choice of form itself, with no question in a round.
> **＋** The `context` of the Case names the choice, and the person sees it at the showing of the Case.
> **＋** A choice of form whose options differ in behaviour, in cost or in what they block is a fork, and it asks that choice in a round.
> **＋** It asks in a round how a Case is checked only where the Case can give no Estimate, or where the options of that question differ in behaviour, in cost or in what they block.
> **＋** A new Case it builds beside a ratified Case takes the number one above the highest number of the case files and of the decision lines of the session's ledger, or the free number that the guard of its case file names, and carries no `{supersedes:case N}` mark.
> **＋** The file of that ratified Case stays as it is, and a pair of the new Case whose sentence the ratified Case changed takes that sentence as the ratified Case leaves it.
> **－** A choice of the bound, of a second reasonable `recommend`, of the exceptions or of what is left not done stays a fork.
> **－** A Case that can give no Estimate still asks in a round what its Estimate will check.
