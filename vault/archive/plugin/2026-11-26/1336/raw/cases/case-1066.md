## Case 1066 — The main agent leaves the number of a changed Case to case-guppi

> **context:**
> When a ratified Case changes in Plan Mode, the main agent sends it back to its `case-guppi`, and the new file is shown and ratified again. The Render of `rule-orchestration` says so, in the paragraph on showing and signing a Case. On the number, that paragraph says only that a Case ratified in Work Mode, none of whose tasks has run, changes under its own number, as in Plan Mode, and so it sets the old number in Plan Mode with no exception, as the root cause of the lesson below says. The rule that a ratified Case that comes back in another shape takes a new number, its decision lines carrying `{supersedes:case N}`, stands in the Splitting section of `vault/wiki/case-schema.md`, which the main agent does not load. In session 2003 the main agent sent the `case-guppi` of Case 1060 back to build under 1060; the check of the case file refused that build, and the Case was built as 1063 superseding 1060, as `lesson-orchestration-case-built-again-in-another-shape-under-its-old-number` records. The person chose to leave the number to `case-guppi` and its check, with a pointer to the rule, and not to copy the rule into `orchestration.md`, so that it stands in one wording. The first pair adds one sentence after the sentence that ends with "(cases 438, 441)" in that paragraph. The second pair rewords the sentence on a Case ratified in Work Mode so that it changes as in Plan Mode, under the number that `case-schema.md` sets for it, and no longer sets the old number with no exception; the other sentences on Work Mode stand, since there a new number is already set. These findings came from `/pre-spec`. Cases 1065 and 1067 are built at the same time as this one, so their files were not read in this build. No Estimate of `rule-orchestration` checks the number: their `purpose` lines were read, and `estimate-orchestration-shows-the-built-case` is the one whose Criterion speaks of a ratified Case that changes. Its lines say the Case changes through its `case-guppi` and is ratified again, and that in Work Mode it is not built again under its own number; the new sentence makes none of them false, so it stands. Making that Estimate check the number too would mean replacing its long Criterion whole, so this Case creates a new Estimate instead. That is a choice of form. > **problem:**
> `orchestration.md` gives the main agent no rule for the number of a ratified Case that comes back in another shape, so the main agent sent back a correct build under a new number.

> **recommend:**
> - **What should the orchestration file say about the number of a ratified Case that comes back changed?**
>   - Recommended: (a) leave the number to case-guppi and point to the rule.
>   - Answer: agreed, (a).

> **given:**
> `rule-orchestration`: its Render sets how a ratified Case changes through its `case-guppi`.
> **＋** `vault/wiki/orchestration.md`: the file rendered from that rule.
> **＋** `estimate-orchestration-leaves-the-number-to-case-guppi`: the new check of the number of a changed Case.
> **＋** `vault/wiki/case-schema.md`: its Splitting sets the new number of a Case that comes back in another shape.

> **when:**
> In Plan Mode, with `vault/wiki/orchestration.md` loaded, the main agent sends a ratified Case back to its `case-guppi` and that `case-guppi` answers with the summary of the Case.

> **then:**
> The main agent asks for no number in its message to `case-guppi`.
> **＋** The main agent shows the Case under the number of the `**Case:**` line of the summary.
> **＋** A new number whose decision lines carry `{supersedes:case N}` is shown as it stands, since the Splitting of `vault/wiki/case-schema.md` sets it.
> **－** The main agent does not send the Case back to be built under its old number.
