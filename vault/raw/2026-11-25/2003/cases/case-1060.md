## Case 1060 — A passed one-off Estimate is not read again

> **context:**
> A one-off Estimate carries `once: true` and targets the live sprint page. It checks one state of the data once, not a behaviour that lasts. Today `case-schema.md` makes no exception for it. A Case that changes a page must give an `update` to each Estimate whose Criterion speaks of the change. That `update` sets the Estimate `pending`, and it must be read again. `case-guppi.md` counts an Estimate that the Case does not name as a contradiction, and `/pre-spec` reports it as a finding (case 203.2). So a passed one-off Estimate, such as one that read the Purpose of `entity-sprint-plugin` once, would be read again each time a later Case changed that Purpose. Case 1057 put the question into the Backlog of `entity-sprint-plugin`. The person chose that a passed one-off Estimate is left alone. A one-off Estimate that is `pending` or `failed` is updated as before, since Case 1057 set that one is worked on until a reading passes. A Case that needs the same state checked again creates a new one-off Estimate. The rule is an instruction to agents in four rendered texts, and the Case adds one sentence to each one. In the Render of `rule-case-protocol`, the full rule goes after the sentence on the Estimates of a changed page. In the Render of `rule-case-build`, a sentence after its definition of a contradiction says that a passed one-off Estimate is none. In the Render of `rule-prespec`, the question on Estimates that a Case does not name sets that Estimate aside. In the description of the field `once` in the Render of `rule-estimates-schema`, a sentence says that such an Estimate is not read again. Each new sentence keeps its pointer in a bracket at its end, since each of the four pages carries `core: true` (case 807.4). The Backlog line leaves `## Backlog` of `entity-sprint-plugin`, and nothing goes into `## Closed`, since the schema of entities keeps closed Slices there and no answered questions; that is a choice of form. The person chose a one-off reading of the four texts on the sprint page. The four files change only at the render of the librarian's run, as `orchestration.md` sets it, so the `method` waits for the librarian's run of this session. That is allowed for an Estimate of a sprint page (case 772.4). No Estimate of the four rules checks this. `estimate-case-protocol-loaded` promises only that `case-schema.md` equals its Render. `estimate-estimates-schema-checked` reads the lists of the schema, and the Case changes only the prose of the field `once`; `.guppi/tests/test_schemas.py` reads only the `properties` and `body` of the live `estimates/schema.yaml`, so it does not fail. `estimate-prespec-reconciles` names the question on Estimates that a Case does not name, and that question stays. The new Estimate checks the exception, so it is not signed twice and that Criterion stands. Of `rule-case-build`, `estimate-case-build-reads-by-need-and-in-parts` and `estimate-case-build-writes-the-case` promise how `case-guppi` reads the `purpose` and the Criterion of the Estimates of a page. The Case does not change that reading, so their Criteria stand. `estimate-sprint-plugin-frontierguard-build-read-its-folders-readers` already says that it is not read again once a reading passes, so it agrees with the new rule. A Grep for `once: true|one-time Estimate|one-off Estimate` over `.claude/` found no file, and `ask-guppi.md` takes the question of `/pre-spec` from its caller, so no other text sets the old rule. The check of this file listed the texts that name the pages and files the Case changes, and they were judged by their purpose lines. `estimate-sprint-plugin-done-counts-a-one-off-reading` is a `pending` one-off Estimate whose Criterion reads the Purpose of `entity-sprint-plugin`, and the Case changes only the Backlog of that page, so it stands. `entity-glossary` holds no term for a one-off Estimate or for the update of the Estimates of a changed page, so it stands. The purpose lines of the other listed texts speak of other things, such as the form of a round, the check of a Case file, the schemas of other categories and the steps of other skills. The ledger of this session holds no `error` lesson.

> **problem:**
> A one-off Estimate checks one state once, but a later Case must set it `pending` and read it again whenever it changes what that Estimate checked. The person decided that a passed one-off Estimate is not read again.

> **recommend:**
> - **Is a passed one-off Estimate left alone by later Cases?**
>   - Recommended: (a) left alone once passed: no `update`, no `pending`, and no missed Estimate at `/pre-spec`; a `pending` or `failed` one is updated as before.
>   - Answer: (a).
> - **How the new rule is checked**
>   - Recommended: (b) a one-off reading of the four texts on the sprint page.
>   - Answer: agreed, (b); the reading waits for the librarian's run of this session, since the four files change at its render.
