## Purpose

Prevents a Case from being shown to the person in a form the checks of pre-spec refuse, or with other `given`, `when`, `then`, `tasks` or `ratification` than the ones that passed them, and a round of `case-guppi` from being shown after a text of the main agent's own (case 562); the Case reaches the person in a file the hook writes from the answer that passed them (case 452.1). Until case 419 no script read a Case before its ratification: the hook of `rule-spec-write` checks it only after the person signed, and a fault of the form was found by the person or at pre-spec ([[insight-case-form-chat-form-read-by-no-script]]). The checks are the ones of pre-spec and of the Spec hook, imported, not copied ([[rule-one-judgment-one-implementation]]); the text of the story sections — `context`, `problem` and `recommend` — is not among them, only their presence, their order, the script of the name, `context` and `problem` of a Case, by the language finding of pre-spec, and the title of each item of `recommend` against the questions of the rounds (case 544.3): the person judges the text (cases 449, 537).

## How it works

`uv run guppi casecheck --subagent` on `SubagentStop`. For an answer of `case-guppi` (`agent_type`), it takes as the answer the newest output of the subagent in `agent_transcript_path` that holds a Case heading — the `message` of a `SubagentHandback` call or the text of an assistant message, whichever stands later — or `last_assistant_message` when the transcript is not readable or holds none, and reads the Cases of the answer by the functions of `guppi/ratified.py` that read the chat form, builds the section of each in the Spec in memory as the `Stop` hook of `rule-spec-write` writes it, and runs `prespec.judge` over them, the decision lines of each `ratification` fence standing for the ledger, and those lines with the decision lines of the session's window naming the categories whose schema rule the session changes, whose `create` and `defer` items `judge` does not judge by their keys (case 436.4), the Frontier left to `/pre-spec` but for one check: for each open line of the session's `frontier.md` whose source is `backlog` and each page of its title that carries `deferred_by`, a Case of the answer that, itself or through a sub-case, names the page on a decision line other than a `defer` gets a finding for each Decision of that list when no Case among it and its sub-cases both names the page and carries its `{supersedes}`, by the function of `guppi/prespec.py` that `/pre-spec` runs (case 467.2). It checks besides the order of the sections and the ones the schema requires, and that `ratification` holds one untagged fence of ledger lines and nothing else; a sub-case that carries `problem` is a finding of that sub-case, since `problem` stands on its parent only (case 544.4). It runs besides the language finding of `/pre-spec`, `check_untranslated` of `guppi/prespec.py`, imported, over the same text: a name, `context` or `problem` of a Case of the answer that holds a letter outside the script of the documentation language `guppi.toml` sets is a finding of that Case, sent back and stored as any other finding, and a `guppi.toml` that is missing or names a code the table does not hold is one finding, given to the first Case of the answer (case 537). It runs besides the comparisons of `guppi/prespec.py` that `/pre-spec` prints as notes: each line of the `## Criterion` of an Estimate that a Case of the answer replaces whole — an `update` that names no part, by `names_a_part` of `guppi/materialize.py` — which no line of the new Criterion equals once the operand, the labels and whitespace are set aside, is a note. A note goes back to `case-guppi` once: the hook exits 2 with the notes on stderr and stores them in the entry of the Case apart from the findings; a note the store already holds for the same Case id is not sent again, the file of the Case is written as for an answer with no finding, and the `Stop` check does not refuse a Case for a note (case 472.1). Each Case of the answer is stored, with its findings and the time of the store, in `<plan>.checked.json` beside the plan file of the session, a later answer for the same id replacing it but for the notes sent for that id, which it keeps (case 472.1). When no Case of the answer has findings, the hook writes the Cases of the answer, as the store holds their text, into `raw/<date>/<hi HHMM>/cases/case-<N>.md`, N the id of the top-level Case — the file replaced whole, or only the section of a sub-case the answer holds alone; `case-guppi` itself writes no file (case 452.1). A finding exits 2 with the findings on stderr, and the agent answers again, whatever `stop_hook_active` says: Claude Code sets it on the second fire after a handback with no exit 2 of the hook. A finding for a Case whose text the store already holds with findings is stored and exits 0, so an unchanged answer is not sent back twice. The hooks read stdin as UTF-8 and never raise. Two `then` lines of two sibling sub-cases of the answer whose shared words of four or more characters make 60 percent or more of the words of the shorter line are a note of the same kind (case 472.2). For an answer that holds a Case, it reads besides the earlier outputs of the subagent in `agent_transcript_path` that hold no Case heading — its rounds — and takes the title of each question from its line `❓ **Q<n>** - **<title>**:`; a title that no item of a `recommend` of the top-level Case or of its sub-cases in the answer opens with, in bold, is a finding of the top-level Case, sent back and stored as any other finding; a title asked in more than one round is looked for once, and the words of an item after its title are not judged (case 544.3). An answer with no Case heading, where no earlier output holds one either, is neither checked nor stored; with no plan file of the session nothing is stored.

`uv run guppi casecheck` on `Stop`, beside `guppi ledger`, `guppi ratified` and `guppi context`, which run in parallel. Each Case the reply shows under its heading with at least one of its sections is compared with the Case of the same id in `<plan>.checked.json` in each of its `given`, `when`, `then`, `tasks` and `ratification` that the reply shows, line by line once line ends and trailing spaces are the same; the name of its heading, its `context`, `problem` and `recommend`, and text under the heading outside its sections are not compared (cases 441, 452.2); a parent shown with its sub-cases is compared part by part. Under the heading of a top-level Case, one `ratification` whose fence holds the ledger lines of its sub-cases — the list of the showing that `rule-case-protocol` sets — is read as the showing of each sub-case whose id a line names: the lines that name that id are compared with the `ratification` of that sub-case in the store, and a stored line that is missing or a line the store lacks is a difference; the Spec hook reads a showing the same way, by the same function (case 561.10). A Case the store does not hold, one that differs, one stored with findings, or one with no `SendUserFile` call on `raw/<date>/<hi HHMM>/cases/case-<N>.md` in the turn of the reply, N the id of its top-level Case, exits 2 with the reason and the findings on stderr; the Spec hook imports the same reading of a sending (case 452.2). A heading with no section — the acknowledging reply — a fence tagged `DIFF`, and a deferred decision in the short form — `context`, `problem` and a fence tagged `then` with `defer` items, no `given` and no `when` — are not compared; on the re-fire (`stop_hook_active`) it exits 0. The same run judges how a round opens (case 562). When the turn of the reply — the records after the person's last prompt, by `turn_of_reply` — holds a round of `case-guppi`, a text that `case-guppi` gives back to an `Agent` or `SendMessage` call and that holds a line `❓ **Q<n>** - **<title>**:` by `QUESTION_LINE`, no Case heading and no first line `**Fact:**`, it exits 2 when the first line of the reply that is not blank opens neither with `❓ ` nor with a bold label that ends in a colon — the label of the Context paragraph, translated — and, while the session's event log holds no `prespec` line of this session after its `hi`, judged by the function the hook of `rule-prespec-hook` uses, when the main agent wrote text in the turn before its last tool call; after `/pre-spec` that text is not judged, since in the loop after its findings each answer of a `case-guppi` comes back in a turn of its own and the text the main agent writes there is set by `rule-prespec` (case 581.2). The reason quotes the text before the round and tells the agent to show the round again with nothing before it. Text after the last question and one horizontal rule is not judged, a turn with no round — the main agent's own questions, a `**Fact:**` answer, a re-pitch by `wait-what` — is not judged, and the check stores nothing. An error of the `Stop` run itself after it has read the payload — an exception while it reads the transcript, the event log or the store, or compares a shown Case or reads a sending — exits 2 with `casecheck: not checked: <error>` and the advice to show the Case again once the cause is fixed on stderr, so the agent sees it at the end of that reply. An empty or unreadable payload exits 0 with its line on stderr. The run of `--subagent` keeps exit 0 with its error on stderr, since a send-back to `case-guppi` is not ended by `stop_hook_active` and would loop; a Case its error left with no file is refused later by the `Stop` check (case 555.1).
